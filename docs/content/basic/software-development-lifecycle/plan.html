Lab 01 — Planificación

3–6 BobCoins
~20 minutos

Toda buena construcción empieza antes de la primera línea de código. En este lab vas a preparar el starter de Bob's Beans, conectarlo a la API, estudiar los mockups y el contrato, y hacer que Bob convierta todo eso en un plan de construcción concreto.

Lo que vas a lograr

  • Ejecutar la aplicación starter y ver las tres pantallas de marcador de posición.
  • Confirmar que la aplicación se comunica con la API de Bob's Beans (ya viene conectada).
  • Entender el contrato de la API y los tres mockups.
  • Usar Bob para producir un plan pantalla por pantalla que seguirás en los Labs 02–04.

El idioma de la aplicación

Las instrucciones y los prompts están en español, pero la aplicación se construye en inglés: mockups, nombres de archivo, funciones y todos los textos visibles de la interfaz. Cada prompt se lo pide a Bob explícitamente. Si Bob genera la UI en español, las pantallas dejan de coincidir con los mockups y el Lab 06 marcará diferencias en todos lados.

Paso 2 — La aplicación ya está conectada a la API

No hay nada que configurar. El starter viene con un .env listo para usar que apunta a la API de Bob's Beans hospedada:

VITE_API_BASE_URL=https://bobs-beans-api.2akfv5yaq586.us-south.codeengine.appdomain.cloud

Pasa directamente a ejecutar la aplicación.

Si tu instructor te da otra URL de API

Abre .env, reemplaza el valor de VITE_API_BASE_URL y reinicia npm run dev: Vite lee .env solo al arrancar. Lo mismo aplica si prefieres correr la API tú mismo: pon VITE_API_BASE_URL=http://localhost:8080 y levántala localmente (ver el README.md de la API).

Paso 3 — Ejecuta el starter

npm install
npm run dev

El navegador abre http://localhost:5173. Deberías ver el header y el footer de Bob's Beans, y tres páginas de marcador de posición "🚧 build me" en /, /product/anything y /cart.

Checkpoint

Si se renderizan el header, el footer y los marcadores de posición, tu entorno está listo. Los marcadores son intencionales: los vas a reemplazar en los próximos tres labs.

Paso 4 — Entiende el contrato de la API

La aplicación habla con la API únicamente a través de src/api/client.js. No vas a escribir llamadas fetch a mano, pero sí necesitas saber qué datos hay disponibles.

MétodoRutaDevuelve
GET/api/productsTodos los productos. Acepta ?category= y ?search=.
GET/api/products/:idUn producto.
GET/api/categories["Single Origin", "Blends", "Decaf", "Equipment"]
POST/api/ordersUna confirmación — siempre tiene éxito.
GET/images/:id.svgLa imagen del producto.

Ábrelas en el navegador:

¿Por qué no hay cuentas ni pagos?

Es deliberado. POST /api/orders acepta cualquier carrito y devuelve al instante una confirmación con un orderId. No hay login, ni dirección, ni pago. Eso mantiene el workshop enfocado en construir UI a partir de un diseño — no en plomería de backend.

Paso 5 — Revisa los mockups

Estas tres capturas son tu fuente de verdad: en cada lab de construcción vas a adjuntar la que corresponda al chat de Bob para que construya a partir de la imagen. También están en tu proyecto, en mockups/, junto con los *.mockup.html de especificación de diseño.

Paso 6 — Pide a Bob el plan de construcción

Ahora convierte el diseño en un plan antes de construir. Cambia Bob a Plan Mode: analiza y propone un plan sin modificar ningún archivo todavía.

Estoy construyendo una tienda de 3 pantallas en este proyecto. El shell de la aplicación,
el ruteo, el carrito (src/cart/CartContext.jsx) y el cliente de API (src/api/client.js)
ya están hechos.

Necesito implementar tres pantallas para que coincidan con los mockups de la carpeta
mockups/:
- Home.jsx + ProductCard.jsx  → mockups/home.png    (usa getProducts)
- Product.jsx                 → mockups/product.png (usa getProduct, addItem)
- Cart.jsx                    → mockups/cart.png    (usa useCart, createOrder)

Lee src/api/client.js y src/cart/CartContext.jsx para conocer las funciones exactas
disponibles. Después dame un plan de construcción corto, pantalla por pantalla: para cada
una, qué datos necesita, qué componentes o secciones crear y qué funciones existentes
llamar.

El código y todos los textos visibles de la UI van en inglés, exactamente como aparecen
en el mockup. No traduzcas la interfaz.

No escribas código todavía. No agregues dependencias ni modifiques el cliente de API.

Cómo se ve un buen plan

Bob debería responder con un plan que use los nombres reales de las funciones del cliente (getProducts, getProduct, createOrder, imageUrl, useCart) y que divida cada pantalla en secciones que se correspondan con los mockups. Si inventa endpoints o propone un backend, devuélvelo a src/api/client.js y al alcance de abajo.

Alcance — qué construimos y qué no

En alcance

  • Las tres pantallas, fieles a los mockups.
  • Leer datos a través del src/api/client.js existente.
  • Carrito en el navegador mediante useCart().
  • Un checkout que siempre confirma.

Fuera de alcance

  • Un backend, una base de datos o endpoints nuevos.
  • Cuentas, login o autenticación.
  • Pagos reales o formularios de dirección y envío.
  • Paginación, listas de deseos, reseñas o un panel de administración.

Mantener el alcance acotado es la lección, no una limitación. Frena a Bob si propone algo de la lista de fuera de alcance.

Criterios de éxito

  • Starter descomprimido y abierto en Bob.
  • npm run dev muestra el esqueleto y los marcadores de posición (el .env incluido ya apunta a la API).
  • Puedes abrir /api/products y un producto individual en el navegador.
  • Revisaste los tres mockups.
  • Bob produjo un plan de construcción pantalla por pantalla que referencia las funciones reales del cliente.
