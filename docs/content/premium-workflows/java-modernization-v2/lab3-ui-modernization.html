Caso de uso: migrar Struts a React

La aplicación utiliza actualmente:

  • Interfaz : Struts / Representación del lado del servidor JSP

Lo migrarás a:

  • Interfaz : React SPA con Material UI
  • Backend : servicios REST estilo Jakarta EE (JAX-RS), reemplazando la capa de acción Struts como fuente de datos de la interfaz de usuario

Por qué esto importa

  • Struts es un marco MVC renderizado por servidor cuyo impulso empresarial se detuvo hace años. La presentación y la lógica empresarial están entrelazadas en acciones y JSP.
  • A React SPA en un backend REST separa los dos claramente: la capa Java se convierte en una API y la interfaz de usuario se convierte en una interfaz implementable de forma independiente. Esa división es lo que hace posible el resto de la modernización (contenedores, escalamiento independiente, un sistema de diseño).

En este snapshot la capa REST ya existe, así que Bob se salta la descomposición del backend. Confirma en un minuto que la API responde: es el contrato sobre el que se va a construir la interfaz, y verificarlo ahora te ahorra depurar más tarde.

Cuando el servidor esté arriba, abre:

Debe devolver JSON con recetas y pedidos.

La UI de Swagger no sirve como comprobación

Si está habilitado mpOpenAPI, Liberty sirve un Swagger interactivo en http://localhost:9081/openapi/ui/, sin raíz de contexto de la aplicación. Es útil para explorar endpoints, pero lo sirve Liberty y no tu aplicación, así que devuelve 200 aunque la API esté dando 404. Confirma siempre con el JSON de /api/dashboard.

Si ves una «Struts Problem Report» en vez de JSON

Significa que el filtro de Struts está interceptando /api/… antes de que lo atienda JAX-RS. El snapshot ya lo evita con esta línea en src/main/resources/struts.xml:

<constant name="struts.action.excludePattern" value="/api/.*" />

Si te falta, es que estás sobre una copia antigua del bundle: vuelve a descargarlo desde el overview. Ojo con el diagnóstico — Struts sirve su página de error con HTTP 200, así que comprobar solo el código de estado no basta; mira que el cuerpo empiece por {.

Si /api/… devuelve 404

Es la raíz de contexto, no una API rota. El server.xml del snapshot fija context-root="/simple-pharmacy", así que la URL de arriba es la correcta. Si algo la reescribió, toma la raíz real del log de arranque:

grep CWWKT0016I target/liberty/wlp/usr/servers/defaultServer/logs/messages.log

La aplicación Struts original sigue funcionando en http://localhost:9081/simple-pharmacy/dashboard. Vale la pena abrirla un momento: es el "antes" que estás a punto de reemplazar.

Solución de problemas

CWWKS9660E: The orb element ... requires a user registry al iniciar el backend

Bob configuró el servidor con la plataforma completa jakartaee-10.0 , que incorpora el Pila ORB/EJB. El ORB espera 10 segundos por un registro de usuarios, no encuentra ninguno y registra "no se iniciará ninguna aplicación". Esta aplicación es REST + JSP solamente ; nunca usa EJB ni ORB - Entonces, el conjunto de funciones correcto es Web Profile . En src/main/liberty/config/server.xml , reemplace la función de la plataforma con el perfil web: 

          <feature>webProfile-10.0</feature>

Mantén todas las funciones mpOpenAPI-* / mpMetrics-* : las funciones MicroProfile funcionan junto con ellas. Reiniciar Liberty; el error desapareció y el inicio es más rápido. La instantánea enviada ya utiliza webProfile-10.0 ; esto solo reaparece si Bob lo cambió por jakartaee-10.0 .

La solicitud de API falló: el chat muestra {\"apiProtocol\":\"openai\"}

Haz clic en Reintentar en la ventana de chat de Bob.

Cada llamada /api devuelve 404

Dos causas diferentes producen esto: verifica primero la raíz del contexto, es la más rápida:

1. Raíz de contexto incorrecta (más común una vez que Struts desaparece). Si Bob implementó la aplicación como simple-pharmacy.war , la base real es /simple-pharmacy.war/api/… , no /simple-pharmacy/api/… ; la línea de inicio CWWKT0016I le indica cuál. La multa por carga de la página Swagger /openapi/ui/ es no tranquilizadora aquí: Liberty la sirve en la raíz del servidor, por lo que funciona incluso cuando cada /api enruta 404. Solucione fijando context-root="/simple-pharmacy" en el elemento <application> en src/main/liberty/config/server.xml (la instantánea enviada ya hace esto).

2. Struts está tragando /api (solo si Struts todavía está en web.xml ). El filtro Struts asignado a /* intercepta las solicitudes REST antes de que JAX-RS las vea. Pregúntale a Bob: 

          Struts está interceptando /api antes de que JAX-RS lo vea. Agrega el struts.action.excludePattern
constante para /api y confirma que existe la clase activadora @ApplicationPath("/api").

Struts 7 coincide con excludePattern con el URI de solicitud completo (incluida la ruta de contexto), por lo que el patrón necesita un .* — .*/api/.* inicial, un /api/.* simple no.

El frontend no puede comunicarse con el backend: conexión rechazada/error CORS

  2. Confirma que ambos servidores se estén ejecutando a la vez: Liberty en 9081 y Vite en 3000.

Después del Paso 5, las páginas se crean pero no muestran datos (tablas/tarjetas vacías)

Primero, verifica en qué paso te encuentras : en el paso 4 aparece una página genérica vacía, y eso es lo esperado : las páginas de datos no existen hasta el Paso 5, así que no hay nada que depurar ahí. Esta entrada es para cuando Bob haya terminado de construir las páginas (Paso 5) y sigan todavía vacías.

En ese momento, el shell React se procesa pero las llamadas a /api fallan silenciosamente. Abre las DevTools → pestaña Red del navegador y vuelve a cargar; si las solicitudes /api/... son 404 , casi siempre es una falta de coincidencia de ruta, no un error de código. Un curl a través del servidor de desarrollo te dice cuál: 

          curl http://localhost:3000/api/dashboard

JSON atrás → el proxy y el backend están de acuerdo; el problema es la deriva del nombre del campo (ver más abajo). 404 → el proxy Vite y la raíz del contexto del backend no están de acuerdo. vite.config.ts reescribe /api/* → /simple-pharmacy/api/* , por lo que la aplicación solo funciona cuando Liberty despliega el WAR en la raíz de contexto /simple-pharmacy . Si Bob lo dejó como simple-pharmacy.war (verifica la línea de inicio CWWKT0016I ), cada llamada da 404 y las páginas quedan en blanco. Arréglalo fijando context-root="/simple-pharmacy" en el elemento <application> de server.xml — el snapshot entregado ya lo hace así para que coincida con el proxy — luego reinicia Liberty .

Una página /openapi/ui/ que funcione no es prueba de que la API funcione

Liberty sirve la interfaz de usuario de Swagger en la raíz del servidor, por lo que se carga incluso en cada ruta /api 404. Confirma siempre con el curl de arriba, no con la página Swagger.

Si las llamadas devuelven 200 pero las páginas aún están vacías, los nombres de los campos oscilan entre los dos mitades. Pregúntale a Bob: 

          Las páginas se muestran pero no muestran datos. Compare los nombres de los campos JSON que devuelven los recursos REST
contra lo que esperan los componentes React y conciliarlos.

Conclusiones clave

  1. El flujo de trabajo realiza la planificación, no solo la escritura : analiza la aplicación Struts, documenta la arquitectura y propone estados objetivo antes de escribir una línea de código.

  4. Por fases y revisable — Análisis → Planificación → Generación → Validación, con una lista de tareas pendientes que puede expandir en cualquier punto para ver exactamente dónde está Bob.
