Walkthrough: Payment API de principio a fin en una sesión

~60 minutos
6 fases condensadas

¿Cuándo usar este recorrido?

Si ya conoces el flujo del lab o quieres completarlo en una sola sesión intensiva, este walkthrough te da los 6 prompts clave — uno por fase — para recorrer el ciclo completo de la Payment API sin detenerte en cada paso de verificación.

Paso obligatorio — antes de cualquier prompt

Punto de partida

Este recorrido usa un proyecto distinto al de Bob's Beans: la Payment API base. Descarga sdlc-lab-payment-api.zip, descomprímelo y abre la carpeta en IBM Bob con File → Open Folder.

File → Open Folder

sdlc-lab-payment-api/
  • En el explorador deben verse src/, __tests__/ y package.json

Ejecuta npm install en la terminal integrada. Duplica .env.example a .env (con API_SECRET_KEY definida) si el proyecto lo trae; revisa el README.md del proyecto para el detalle. El servidor arranca con npm start.

Paso 1 — Plan: backlog del sprint

Plan Mode Activa Plan Mode y envía este prompt:

Soy PM de una SaaS Payment API (Node.js + Express + SQLite). Tenemos estos problemas:
- Secreto hardcoded en src/routes/payment.js
- Inyección SQL en consultas de pagos
- Endpoint POST /coupons/apply sin implementar (solo skeleton)
- Cobertura de Jest bajo el 60%

Crea un backlog de sprint clasificando cada ítem como Critical Bug (P0), New Feature (P1) o Technical Debt (P2), con criterio de aceptación y estimación en puntos.

Resultado esperado

Backlog con 4 ítems: 2× Critical Bug/P0, 1× New Feature/P1, 1× Technical Debt/P2. Anota los criterios de aceptación — los usarás en los tests.

Paso 2 — Diseño: contrato del endpoint

Ask Mode Cambia a Ask Mode con el archivo openapi.yaml abierto:

Analiza el openapi.yaml de este proyecto y para el endpoint POST /api/v1/coupons/apply indica:
1. Campos requeridos en el body y sus tipos
2. Estructura exacta de la respuesta 200
3. Código HTTP para cupón inválido o inactivo
4. Flujo de secuencia: Cliente → Router → SQLite (los 3 casos: feliz, no encontrado, inactivo)

Con ese flujo genera la especificación para un diagrama de secuencia en draw.io.

Resultado esperado

Especificación clara: body = { code, originalAmount }, respuesta 200 con finalAmount y savings, error 400 para cupón inactivo. Diagrama con 3 flujos listos para dibujar.

Paso 3 — Código: corrige las vulnerabilidades

Agent Mode Activa Agent Mode con auto-approve OFF:

En src/routes/payment.js hay dos vulnerabilidades críticas:
1. API Key hardcoded: reemplaza `"SECRET_API_KEY_12345"` por `process.env.API_SECRET_KEY` y agrega un guard si la variable no está definida.
2. Inyección SQL: parametriza las dos consultas que concatenan userId e id directamente en el string SQL.

Muéstrame cada diff por separado antes de aplicar. No modifiques otros archivos.

Resultado esperado

Dos diffs separados: el primero elimina el string hardcoded, el segundo reemplaza interpolaciones por ?. Ningún secreto ni variable de usuario dentro del string SQL.

Paso 4 — Código: implementa el endpoint de cupones

Agent Mode Continuando en Agent Mode:

Implementa el endpoint POST /apply en src/routes/coupon.js reemplazando el skeleton de TODOs.

Lógica requerida:
- Validar que `code` y `originalAmount` existen en el body (400 si falta alguno)
- Buscar cupón por code con consulta parametrizada
- 400 si no existe, 400 si active !== 1
- finalAmount = originalAmount * (1 - discount_percent / 100), redondeado a 2 decimales
- savings = originalAmount - finalAmount, redondeado a 2 decimales
- Responder 200 con { coupon: { code, discount_percent }, originalAmount, finalAmount, savings }

Muéstrame el diff completo antes de aplicar.

Resultado esperado

El bloque res.status(501) desaparece. Prueba rápida: curl -X POST localhost:3000/api/v1/coupons/apply -H "Content-Type: application/json" -d '{"code":"IBMBOB20","originalAmount":100}' debe devolver finalAmount: 80.

Paso 5 — Test y Deploy: verde y contenedor

Agent Mode Ejecuta los tests y optimiza el Dockerfile en el mismo contexto:

Primero, ejecuta la suite completa en la terminal:

npm test

Si todos los tests pasan, envía este prompt a Bob en Agent Mode para optimizar el Dockerfile:

Optimiza el Dockerfile: cambia node:18 por node:18-alpine,
agrega usuario no-root appuser y una instrucción HEALTHCHECK a /health

Resultado esperado

Todos los tests en verde (incluyendo el test de SQL injection y los de cupones). Dockerfile con node:18-alpine y usuario no-root. Imagen construida en menos de 60 segundos.

Paso 6 — Mantener: logs y cierre del ciclo

Ask Mode Cambia a Ask Mode para la revisión final:

Analiza estos dos eventos de producción de la Payment API:

1. SQLITE_BUSY: database is locked — 47 errores en 5 minutos, 12 usuarios afectados
2. 401 Unauthorized desde IP 192.168.1.50 — 340 requests en 60 segundos (brute force)

Para cada uno: causa raíz, impacto en usuarios, solución inmediata y medida preventiva.

Luego genera el CHANGELOG.md versión 1.1.0 con secciones: Fixed (2 bugs de seguridad), Added (endpoint /coupons/apply), Changed (Dockerfile optimizado a alpine).

Resultado esperado

Análisis de ambos eventos con soluciones concretas (WAL mode + rate limiting). CHANGELOG.md generado y listo para hacer commit. Ciclo cerrado.

✅ Checklist de cierre rápido

  • Backlog con 4 ítems clasificados correctamente
  • Sin secretos hardcoded ni interpolaciones SQL en el código
  • Endpoint POST /coupons/apply funcional (200 y 400)
  • 100% tests en verde con cobertura ≥ 80%
  • Dockerfile con node:18-alpine y usuario no-root
  • CHANGELOG.md con los cambios del sprint

¿Quieres profundizar?

Cada fase tiene su propia pestaña con prompts adicionales, respuestas esperadas detalladas y gates de aprobación. Usa las pestañas Plan, Diseño, Código, Test, Deploy y Mantener para el recorrido completo.
