Step 3. Publicar 20 mensajes de ejemplo

Los 20 mensajes simulan ventas y reposiciones reales de Voltia, para que los agentes del Track F encuentren datos desde el primer momento.

¿Qué hace run_in_cluster.sh produce_messages internamente?

Empaqueta produce_messages.py y el .env en un ConfigMap, lanza un Job de Kubernetes en el namespace confluent y el pod produce 20 mensajes JSON_SR al tópico inventory.transactions usando las credenciales SASL del .env. Cada mensaje incluye:

  • Campos sku, branch, quantity, transaction_type, timestamp, source y reference — validados por el JSON Schema registrado en Step 1b.
  • Variedad de tipos: ADDITION, SALE y ADJUSTMENT — para que ksqlDB calcule disponibilidades reales.
  • Si ksql materializa bien, inventory.availability (sin .flink.) se actualiza al llegar el primer mensaje. Si la query está Running y ese tópico sigue vacío, no es que “falte Flink”: el CTAS no está emitiendo. Avísale al facilitador.

Flujo completo — los mensajes publicados en inventory.transactions son procesados por ksqlDB y el resultado llega a inventory.availability en tiempo real:

Consulta la tabla de disponibilidad directamente desde el endpoint externo de ksqlDB:

curl -sk -u admin:<KSQLDB_PASSWORD> \
  https://<VM_IP>/ksqldb/query \
  -H "Content-Type: application/vnd.ksql.v1+json" \
  -d '{"ksql":"SELECT * FROM INVENTORY_AVAILABILITY LIMIT 5;","streamsProperties":{}}'

Deberías ver 5 filas con sku, branch y available_quantity.

Step 4b. Inspeccionar payloads, timestamps y offsets en la consola web

Verificar visualmente los mensajes en la plataforma web confirma que el pipeline completo funciona: el productor emitió JSON_SR, Kafka validó el schema y ksqlDB procesó los datos hacia inventory.availability.

  1. 🌐 Entorno En la consola web, navega al tópico inventory.transactions y haz clic en la pestaña Messages o Live Tail.
  2. Configura el visor para leer desde el inicio: selecciona From Beginning / Earliest en el selector de offset.
  3. Haz clic en cualquiera de los mensajes para abrir el panel de detalle y verifica:
    • Offset y Partición — confirma en cuál de las particiones se almacenó el evento (debe ser partición 0 con 1 sola partición).
    • Timestamp — fecha y hora exacta de emisión registrada por el broker.
    • Payload (cuerpo) — comprueba que el JSON incluye los campos: sku, branch, quantity, transaction_type, timestamp, source y reference.
  4. Navega al tópico inventory.availability y verifica que ksqlDB ya calculó filas con available_quantity actualizada para cada SKU/sucursal de los eventos emitidos.

✓ Checkpoint 4b (Final)

  • Se visualizan los mensajes en la pestaña Messages con sus timestamps y offsets correctos.
  • El payload cumple el JSON Schema registrado en Step 1b (campos sku, branch, quantity, transaction_type, timestamp, source, reference).
  • El tópico inventory.availability (el de ksql, sin .flink.) muestra disponibilidad por SKU y sucursal. Ese es el que lee el MCP en Track F. El tópico Flink es otra demo: puede tener datos y aun así Track F falla si el de ksql está vacío.
  • El subject inventory.transactions-value en Schema Registry sigue mostrando versión v1 sin errores de validación.

  • Tópico inventory.availability se actualiza automáticamente con cada transacción.
  • Tópico inventory.availability.flink con el job Flink en RUNNING (lab ksqlDB / setup.sh -s 4).
  • 20 mensajes publicados en inventory.transactions y visibles en la consola web.

Troubleshooting — Errores frecuentes

Referencia rápida para resolver los problemas más comunes durante el workshop.

Síntoma / Error Causa probable Solución inmediata
Permissions 0644 for .pem are too open Permisos incorrectos en la llave SSH (macOS/Linux). En Mac/Linux: chmod 600 cflt-vsi-key.pem o el script repair_cflt_pem.sh. En Windows no uses chmod: icacls cflt-vsi-key.pem /inheritance:r /grant:r "%USERNAME%:F" o repair_cflt_pem.ps1.
Load key … invalid format En Windows el pegado deja CRLF. El wrap nativo de OpenSSH es 70 columnas; forzar solo 76 puede empeorar un PEM ya correcto. Corre repair_cflt_pem.ps1 (Windows) o repair_cflt_pem.sh (Mac). Normaliza LF, prueba wrap 70 y luego 76. No regeneres la clave ni la pegues en el chat.
PEM de 0 bytes / Bob pide el contenido de la clave El editor no guardó el archivo (autosave off). Pega BEGIN→END, pulsa Ctrl+S / Cmd+S y reintenta el Paso 0. No pegues el PEM en Bob.
Connection timed out al puerto SSH (22) Casi siempre la IP está truncada (cuatro octetos: 163.66.83.162, no 163.66.83.16). No es falta de OpenSSH ni de la extensión CCH. Relee la IP en TechZone (Log in to the VM) y en el prompt. No escanees puertos ni intentes SSH por 443/80. Solo si la IP está completa, revisa firewall.
Schema validation failed al publicar mensajes El JSON del evento no coincide con los tipos definidos en el Schema. Asegúrate de que quantity sea entero (no string) y que transaction_type sea uno de: ADDITION, SALE, ADJUSTMENT.
Topic already exists El tópico ya fue creado en un intento previo. El script lo detecta y lo omite sin error. Si deseas empezar de cero ejecuta ./setup.sh -c para limpiar el entorno.
No se ven mensajes en el Web UI El filtro de mensajes está en Offset Actual en lugar de Inicio. Cambia el selector de visualización a From Beginning / Earliest en la pestaña Messages del tópico.
No module named 'httpx' / to_dict must be callable / Missing required JSON schema annotation title ZIP viejo (productor / pip sin pin). Descarga de nuevo el bundle desde el diálogo del hub (TechZone + número). El overlay pinnea confluent-kafka==2.6.1 y registra el schema en -s 1.
Supported values are: [confluent] o Flink en crash-loop SQL OSS (connector=kafka) o timeout de transacciones en el broker. No inventes el job: ./setup.sh -s 4. Si ves Column 'SKU' not found … sku, re-descarga el ZIP (INSERT con sku/quantity). Si un INSERT queda PENDING/FAILED, bórralo para no saturar el compute pool compartido.
inventory.transactions tiene mensajes; inventory.availability (sin .flink.) está vacío. Persistent query Running El CTAS de ksqlDB consume los offsets JSON_SR y no emite filas al sink. Flink sí puede llenar inventory.availability.flink (otro tópico). El MCP de Track F no lee Flink. No reescribas el SQL ni cambies el toolkit a Flink. Vuelve a correr ./setup.sh -s 3: después del produce corre materialize_availability.py, que solo llena inventory.availability (ksql / Track F) si ese sink sigue vacío. No escribe en .flink..
Schema validation failed en Schema Registry El payload JSON no respeta el JSON Schema: un campo numérico (quantity) llega como string, o falta un campo requerido. Verifica que quantity sea entero (no "50" sino 50), que transaction_type sea uno de ADDITION, SALE, ADJUSTMENT y que todos los campos del schema estén presentes. El subject namespaced es $TOPIC_NAME-value. Consulta con las variables del .env (no pidas el password): curl -sk -u "admin:${SCHEMA_REGISTRY_PASSWORD}" https://$HOST/sr/subjects/${TOPIC_NAME}-value/versions/latest
