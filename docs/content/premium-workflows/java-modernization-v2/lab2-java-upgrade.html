Caso de uso: actualizar las versiones de Java

La aplicación se ejecuta actualmente en:

  • Tiempo de ejecución : Liberty, Java 8
  • Interfaz : Struts 2.5.x
  • Espacio de nombres : javax.* (Java EE)

Lo modernizarás para:

  • Tiempo de ejecución : Liberty, Java 21 (IBM Semeru)
  • Interfaz : Struts 7.x
  • Espacio de nombres : jakarta.* (Jakarta EE 10)

Por qué esto importa

Java 21 es la versión LTS actual. Más allá del rendimiento, desbloquea características del lenguaje (registros, tipos sellados, coincidencia de patrones, subprocesos virtuales) y líneas base de dependencia modernas. La medida también arrastra dos migraciones del mundo real que hacen que este laboratorio sea interesante: el cambio de nombre del espacio de nombres javax → jakarta , y un salto de versión principal Struts que cambia el lugar donde vive ActionSupport .

Este es el laboratorio más largo y propenso a fallas del grupo.

El propio Bob califica esta migración como Complejidad: Muy alta , y se lo merece. Tres cosas cambian a la vez (el JDK, el espacio de nombres de Yakarta y la versión principal Struts) y la aplicación no se ejecutará hasta que los tres se alineen, más la configuración del servidor Liberty que Bob no siempre actualiza por sí solo.

Presuponga más tiempo que los laboratorios 1 y 3, espere pegar un par de errores nuevamente en el chat y trabaje en la sección Solución de problemas en lugar de evitarla. Todo lo que golpearás está documentado allí.

2.6 Actualización: aprobar los cambios pom.xml

Bob analiza los problemas que encuentra y explica cada uno de ellos antes de cambiar nada. El que todos ven:

Javassist POM advertencia. "La solución agrega una entrada <dependencyManagement> para fijar org.javassist:javassist a 3.29.2-GA y elimina la declaración directa redundante <dependency> . Esto suprime la advertencia al evitar que Maven evalúe la falla 3.20.0-GA POM durante la recolección."

Haga clic en "Sí, aplique el cambio a pom.xml ". Confirme que la versión dice 3.29.2-GA , igual que Lab 1. Nada en la aplicación importa javassist directamente (es un Struts/OGNL interno), por lo que descartar la declaración directa es seguro.

Apruebe cualquier anulación de dependencia adicional a medida que aparezca.

Por qué mover el pin a <dependencyManagement> es la decisión correcta

Un <dependency> directo fuerza la versión, según la regla más cercana-victoria de Maven. Pero eso solo se aplica después de Maven ya recorrió el gráfico y analizó el 3.20.0-GA POM roto, que es lo que emite la advertencia en primer lugar.

<dependencyManagement> se aplica durante la dependencia colección , antes de que se lea POM. El mismo classpath resultante, pero el POM malo nunca se toca. Esa es la diferencia entre suprimir un síntoma y eliminar la causa, y "fijarlo en la gestión de dependencias, no como una dependencia directa" es la lección transferible para cualquier código base Java real.

Este es el momento más instructivo en el laboratorio.

El salto Struts 2.5 → 7 mueve ActionSupport a un paquete completamente diferente. En un proyecto real, eso implica buscar y reemplazar en cada clase de acción, además de una ronda de errores de compilación que perseguir.

Observe la causalidad , no solo la diferencia: la corrección CVE es lo que fuerza el salto de versión , y la reescritura de importación es lo que hace que se compile nuevamente . Nadie se propuso actualizar Struts hoy; la seguridad lo hizo. Así es como se priorizan las actualizaciones del marco en el mundo real, y es una demostración mucho más honesta que "actualicemos porque lo más nuevo es mejor".

Punto de control: cómo se ve una actualización terminada

Solución de problemas

Comience aquí si la aplicación no aparece

Trabaja estos en orden: se apilan y cada uno puede enmascarar los que están debajo:

  1. Un Liberty obsoleto retiene el puerto → cada corrección silenciosa no hace nada.
  2. Liberty comenzó sin funciones ( CWWKF0001E ) → nada escucha en el puerto.
  3. server.xml todavía tiene características Java-EE → Raíz de contexto no encontrada .
  4. struts.xml apunta a una DTD que no existe → Struts el filtro no se carga.
CWWKF0001E: A feature definition could not be found for servlet-6.0 (el servidor 'se inicia' pero nada responde)

El registro muestra que el servidor apareció – CWWKF0011I: ... started – pero un par de líneas arriba dice: 

          CWWKF0001E: No se pudo encontrar una definición de característica para servlet-6.0
CWWKF0011I: El servidor defaultServer instaló las siguientes funciones: [].

Una lista de funciones vacía . El Liberty que descargó la compilación es un kernel simple que no contiene servlet-6.0 / pages-3.1 , por lo que no se inicia ningún contenedor web y se rechazan todas las solicitudes (curl muestra 000 ) o 404. Esto es diferente de la falta de coincidencia server.xml a continuación: allí las funciones tienen nombres incorrectos; aquí están ausentes del tiempo de ejecución por completo .

Esto ahora se evita en el pom.xml , enviado, que fija un tiempo de ejecución completo en liberty-maven-plugin : 

          <runtimeArtifact>
    <groupId>io.openliberty</groupId>
    <artifactId>openliberty-runtime</artifactId>
    <version>26.0.0.5</version>
    <type>zip</type>
</runtimeArtifact>

Si aún lo presiona (por ejemplo, Bob reescribió el bloque del complemento durante la actualización), restaure ese bloque o instale las funciones en el servidor actual una vez:

          mvn liberty:install-feature

Luego mvn liberty:run nuevamente.

Raíz de contexto no encontrada en el navegador (comience aquí)

Liberty se está ejecutando, pero su aplicación no está implementada en la URL que solicitó. Tres posibles causas, en el orden que vale la pena comprobar:

1. Estás en la URL incorrecta. Bob generalmente establece context-root="/simple-pharmacy" , por lo que la URL del Laboratorio 1 ( /simple-pharmacy.war/dashboard ) ya no funciona. Tome la URL del registro de inicio: 

          grep CWWKT0016I target/liberty/wlp/usr/servers/defaultServer/logs/messages.log

2. Un servidor obsoleto está respondiendo. Busque esto en el registro: 

          CWWKO0221E: La inicialización defaultHttpEndpoint del canal TCP no ha sido satisfactoria.
La vinculación del socket no se realizó correctamente para el host * y el puerto 9081. Es posible que el puerto ya esté en uso.

Eso significa que su nuevo servidor nunca obtuvo el puerto ; un Liberty más antiguo todavía sirve la versión antigua y defectuosa. Mátalo y reinicia: 

          lsof -ti:9081,9443 | xargs kill -9

3. La aplicación no pudo iniciarse. Busque CWWKZ0002E ; consulte las dos entradas siguientes.

CWWKZ0002E / CWWKC2263E: ... specifies version 60, which is higher than the current provisioned version 31

La falla más común en esta práctica de laboratorio. Bob migró la aplicación a Jakarta EE 10 pero dejó la configuración del servidor Liberty en el antiguo conjunto de características de Java EE. web.xml ahora declara Servlet 6.0; server.xml todavía proporciona Servlet 3.1. La aplicación no puede iniciarse, por lo que nunca se registra ninguna raíz de contexto, lo que aparece como Raíz de contexto no encontrada .

Solución: pega la línea CWWKC2263E en el chat de Bob. Resuelve esto bien por sí solo, reemplazando la lista de funciones en src/main/liberty/config/server.xml con los Jakarta EE 10 equivalentes.

Si prefieres arreglarlo a mano, reemplaza todo el bloque <featureManager> con: 

          <featureManager>
    <feature>servlet-6.0</feature>
    <feature>pages-3.1</feature>
</featureManager>

Luego reconstruya y reinicie.

Elimina mpMetrics-1.1 si está ahí

El paquete de migración lo agrega, nada en esta aplicación lo usa y depende en gran medida de servlet-3.1 , por lo que entrará en conflicto con servlet-6.0 y bloqueará el inicio. jdbc-4.1 también puede funcionar; no hay dataSource (la aplicación usa repositorios en memoria).

Filter [struts2]: could not be initialized / FileNotFoundException: http://struts.apache.org/dtds/struts-7.0.dtd

Bob señaló struts.xml a una DTD que no existe. Habiendo actualizado Struts a 7.x, mejoró el DOCTYPE para que coincidiera, pero Apache nunca publicó una DTD 7.0. struts2-core incluye DTD solo hasta 6.5 , por lo que Struts no puede resolverlo localmente, recurre a buscarlo a través de HTTP, obtiene un 404 y el filtro muere. Entonces la aplicación no sirve para nada.

Solución: abra src/main/resources/struts.xml y configure DOCTYPE en una versión que realmente exista: 

          <!DOCTYPE struts PUBLIC
    "-//Apache Software Foundation//DTD Struts Configuration 2.5//EN"
    "http://struts.apache.org/dtds/struts-2.5.dtd">

Luego reconstruya y reinicie. 2.5 está incluido dentro de struts2-core y es lo que utiliza el resto de este taller; Struts 7 lo lee felizmente.

Bob no encontrará este por sí solo.

A diferencia de la falta de coincidencia server.xml , pegar este error en el chat a menudo hace que Bob busque una clase faltante o un problema de ruta de clase. Aplique la corrección DOCTYPE directamente.

Por qué vale la pena mostrar este en la habitación

El razonamiento fue perfecto: "Struts ahora es 7.x, por lo tanto, el DTD debe ser struts-7.0.dtd ." Consistente, plausible y completamente ficticio: el artefacto simplemente no existe.

Es un claro ejemplo de una respuesta incorrecta segura que la compilación no puede detectar . mvn clean compile pasa, el resumen de modernización es verde y la falla solo aparece en tiempo de ejecución cuando Struts intenta resolver la DTD a través de la red. Esta es exactamente la razón por la que existe el paso ejecutar y por qué "compiló" nunca es lo mismo que "funciona".

JSPG0303W / JSPG0236E: failed to load the TagLibraryValidator class [javax.servlet.jsp.jstl.tlv.PermittedTaglibsTLV]

Inofensivo: estas son advertencias, no errores. Un javax.servlet:jstl:1.2 sobrante se encuentra en el classpath y el motor JSP de Jakarta no puede analizar su TLD de la era javax. Ninguno de los JSP de esta aplicación usa JSTL (solo usan /struts-tags ), por lo que nada se rompe.

Para silenciarlo, elimine la dependencia javax.servlet:jstl de pom.xml o simplemente ignórelo.

Conclusiones clave

  1. Un flujo de trabajo, muchos subtipos : Lab 1 (Liberty) y Lab 2 (Java) son el mismo flujo de trabajo con una selección diferente; el panel oscurece lo que no corresponde.
  2. Bob instala sus propias herramientas : el JDK de destino no es un requisito previo que deba satisfacer manualmente.
  3. La seguridad impulsa las opciones de versión : el escaneo CVE es lo que obliga a Struts a 7.x; el espacio de nombres y las reescrituras de importación son consecuencias posteriores. Así es como se priorizan las actualizaciones reales.
  4. Bob posee las partes aburridas : los cambios de nombre del espacio de nombres y las reescrituras de importación en toda una base de código se convierten en un bucle agente que usted aprueba, no en una tarea manual.

  6. Las migraciones se filtran en los bordes : Bob manejó miles de líneas de reescritura de espacios de nombres sin problemas y luego tropezó con dos archivos de configuración. Espere que el código generado sea mejor que la configuración generada y revíselo en consecuencia.
