Caso de uso: buscar y corregir dependencias vulnerables

Cada aplicación Java depende de bibliotecas de terceros, directamente (declaradas en pom.xml ) o transitivamente (extraídas por otra biblioteca). Cualquiera de ellos puede portar vulnerabilidades conocidas catalogadas como CVEs. La detección de vulnerabilidad de dependencia significa:

  • Escaneando las dependencias declaradas y transitivas del proyecto
  • Coincidencia con bases de datos CVE publicadas
  • Informes cada coincidencia con gravedad, versiones afectadas y una solución

  • Remediando actualizando o excluyendo la biblioteca vulnerable

  • Antes : aplicación de farmacia con versiones de dependencia vulnerables en pom.xml

  • Después : dependencias vulnerables actualizadas, resultado de escaneo limpio, rastro de corrección documentado

¿Qué se esconde en este proyecto?

Se plantean deliberadamente tres vulnerabilidades. Bob debería encontrar los tres:

# dependencia Versión vulnerable CVE/GHSA Gravedad Versión reparada
1 commons-text 1.9 CVE-2022-42889 ( Text4Shell ) Crítico (CVSS 9.8) 1.10.0
2 snakeyaml 1.30 GHSA-mjmj-j48q-9wg2 Alto 2.0
3 commons-lang3 3.11 GHSA-j288-q9x7-2f5v Alto 3.18.0
Lo que realmente hace cada uno (léelo después de haber escaneado)

1. Text4Shell: CVE-2022-42889. StringSubstitutor en commons-text admite prefijos de interpolación más allá de la simple sustitución de variables: ${script:…} , ${url:…} , ${dns:…} . Si alguna parte del mapa de sustitución contiene información controlada por el atacante, se trata de ejecución de script arbitraria, exfiltración de DNS o recuperación de URL. En esta aplicación, se puede acceder a él a través de LabelTemplateService , que genera etiquetas de dispensación de medicamentos a partir de una plantilla.

2. RCE de deserialización de SnakeYAML: GHSA-mjmj-j48q-9wg2. El constructor predeterminado new Yaml() felizmente crea instancias de clases Java arbitrarias a las que se hace referencia en YAML (por ejemplo, !!java.net.URL ). La carga de YAML controlado por un atacante se convierte en una instanciación de clase arbitraria y un RCE potencial. Aquí se puede acceder a él a través de FormularyLoader , que carga formulary.yaml para decidir las categorías de medicamentos aprobados.

3. Commons Lang3 recursividad incontrolada — GHSA-j288-q9x7-2f5v. Ciertas entradas desencadenan una recursividad ilimitada y una denegación de servicio por desbordamiento de pila. commons-text:1.9 tira de commons-lang3:3.11 transitivamente; se declara explícitamente aquí en esa misma versión para que el escaneo pueda detectarlo y fijarlo.

Observe la forma de esto: dos de los tres son solo interesantes porque el código de la aplicación realmente les llega. El tercero es un problema puro de gráfico de dependencia. El triaje real se parece exactamente a esta mezcla.

Paso 2: ejecute el flujo de trabajo Java Vulnerabilities Detection

Objetivo

2.1 Iniciar el flujo de trabajo

Haga clic en Inicio en el flujo de trabajo Java Vulnerabilities Detection . 2.2 Detección de dependencia

Bob lee pom.xml , resuelve el árbol de dependencia completo (directo y transitivo) e informa cuántos paquetes escaneará.

2.3 búsqueda de CVE

Bob consulta la base de datos CVE para cada paquete detectado. Esto es rápido: normalmente menos de 30 segundos para un proyecto de este tamaño.

2.4 Informe de hallazgos

Bob informa cada vulnerabilidad con:

  • Paquete y versión afectados
  • Identificadores CVE
  • Gravedad (crítica, alta, media, baja)
  • Si la dependencia es directa o transitiva
  • Remediación sugerida

Punto de control: el escaneo encontró el CVEs plantado

Bob debe informar como mínimo CVE-2022-42889 (Text4Shell), GHSA-mjmj-j48q-9wg2 (SnakeYAML RCE) y GHSA-j288-q9x7-2f5v (lengua común3). SnakeYAML a menudo muestra varios CVEs a la vez, así que no se sorprenda si cuenta más de tres.

Paso 3: revisar los hallazgos

Objetivo

Comprenda lo que Bob encontró y priorice antes de remediar.

3.1 Lea cada hallazgo

Para cada CVE, tenga en cuenta:

  • ¿La biblioteca vulnerable se declara directamente o se extrae transitivamente ?
  • ¿Qué versión fija recomienda Bob?
  • ¿Cuál es la gravedad? ¿Se aplica a cómo esta aplicación utiliza realmente la biblioteca?

3.2 Agrupar los hallazgos

Pregúntate:

  • ¿Cuáles son soluciones rápidas (un aumento de versión única)?
  • ¿Cuáles necesitan excluir una dependencia transitiva y agregar un reemplazo directo?
  • ¿Hay duplicados causados por múltiples rutas que traen la misma versión vulnerable?

3.3 Confirme que comprende cada CVE antes de corregirlo

Si tienes algo que no te resulte familiar, pregúntale directamente a Bob:

        Explique CVE-2022-42889 en términos sencillos y cómo podría afectar esta aplicación.
Gravedad no es lo mismo que riesgo: este es el objetivo del ejercicio

Un CVE crítico en una biblioteca cuyo método vulnerable nunca llama tiene un riesgo real menor que un alto en una ruta activa. Dos de los tres hallazgos de este proyecto son accesibles desde el código de la aplicación ( LabelTemplateService , FormularyLoader ); el tercero es un problema puro del gráfico de dependencia sin ningún sitio de llamada.

El escáner informa severidad . Sólo tú puedes juzgar alcanzabilidad . Hacer esa distinción en voz alta, para cada uno de los tres, es lo que convierte esto de una tarea de cambio de versiones a una clasificación de seguridad.

Paso 4: remediar

Objetivo

Aplique las correcciones propuestas por Bob a través del flujo de corrección interactivo.

4.1 Iniciar la corrección

En el panel del workflow, confirma la subtarea de remediación (elige Sí / aprobar cada fix). Recorre los CVEs uno a la vez. No pegues un prompt en el chat para esto.

4.2 Flujo de aprobación interactivo

Para cada hallazgo, Bob:

  • Explicar el CVE y su impacto.
  • Proponer un cambio pom.xml específico (aumento de versión, exclusión + dependencia directa, pin <dependencyManagement> )
  • Solicite aprobación antes de aplicar

4.3 Vista previa de ediciones individuales

Si no está seguro acerca de un cambio, elija la opción para ver primero las ediciones exactas de pom.xml : Bob representa la diferencia para su revisión.

4.4 Aprobar iterativamente

Trabaje en cada CVE en el orden en que Bob los presenta. Aplica cada edición y luego continúa.

4.5 Manejar los efectos en cadena

Algunas correcciones desencadenan problemas secundarios: por ejemplo, una actualización de una versión importante que requiere un cambio de API en otro lugar. Bob los identifica y solicita aprobación para las correcciones adicionales.

Paso 5: verificar

5.1 Compilar verificación

En la terminal de Bob:

        mvn clean compile

Deberías ver BUILD SUCCESS .

El salto de SnakeYAML 1.30 → 2.0 es una verdadera actualización de la versión principal: mire esta

SnakeYAML 2.0 reforzó el comportamiento del constructor predeterminado, que es precisamente por qué corrige el RCE y precisamente por qué puede romper el código de llamada que dependía de la antigua permisividad.

Si FormularyLoader deja de compilarse o se inicia en tiempo de ejecución, no es un error: es la solución de seguridad que está haciendo su trabajo. Pega el error en Bob y deja que concilie el cambio de API. La lección que vale la pena exponer claramente es que las actualizaciones de seguridad tienen un costo y "rompió algo" no es una razón para omitirlas.

5.2 Vuelva a ejecutar el flujo de trabajo

Haga clic en Inicio en Java Vulnerabilities Detection nuevamente. Bob ahora debería informar cero hallazgos , o una lista sustancialmente reducida.

5.3 Opcional: ejecutar el servidor Liberty

Solución de problemas

El flujo de trabajo informa cero vulnerabilidades en el primer escaneo

Ése es un resultado legítimo en un proyecto limpio, pero no en éste. Significa que pom.xml no contiene las versiones intencionalmente vulnerables que espera el laboratorio. Comprueba que el workflow está apuntando a la instantánea inicial de snapE-* y no la has modificado. pom.xml debe declarar commons-text:1.9 , snakeyaml:1.30 y commons-lang3:3.11 .

mvn compile falla después de un aumento de versión

Una solución actualizó una biblioteca a una versión con un cambio importante en la API. Pegue el error de compilación nuevamente en Bob y pídale que lo concilie; adaptará el código de llamada o propondrá una versión diferente y aún segura. La actualización SnakeYAML 2.0 es la culpable más probable.

Una dependencia vulnerable es transitiva y no se actualizará limpiamente

El CVE vive dentro de una dependencia transitiva que Bob no puede simplemente cambiar de versión, porque otra biblioteca requiere la versión anterior. Bob normalmente propone un bloque <exclusions> en la dependencia externa más una declaración directa de la versión fija. Aprobar cuando se le solicite.

La terminal de Bob muestra la versión de Java incorrecta

sdk use tiene alcance de shell y no se aplica a través de pestañas de terminal ni al terminal que Bob abre por sí solo. Ejecútelo en la terminal de Bob específicamente: 

          sdk use java 21.0.11-zulu

Conclusiones clave

  1. Tus dependencias son tu superficie de ataque : la mayor parte del código de una aplicación Java no es código que tú escribiste. Text4Shell entró a través de una biblioteca en la que nadie pensó.
  2. Recuentos transitivos — commons-lang3 llegaron a través de commons-text . Escanear solo lo que se declara en pom.xml lo habría perdido por completo.
  3. Severidad ≠ riesgo : la accesibilidad decide la exposición real. El escáner clasifica; tu clasificación.
  4. Las correcciones tienen consecuencias : SnakeYAML 2.0 corrige el RCE by rompiendo el comportamiento permisivo en el que se basa algún código. Las actualizaciones de seguridad no son gratuitas y esa no es razón para omitirlas.
  5. Vuelva a escanear para probarlo : la corrección no se realiza cuando llega la edición, se realiza cuando el escaneo está limpio.
