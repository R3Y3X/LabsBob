Lab 3 — Código seguro

Añade reglas de seguridad y coordina un Actor que genera código con un Critic que lo revisa en aislamiento.

2 skills (Actor + Critic)
1 rule de seguridad
3 estándares (NIST · ASVS · CWE)
8–15 BobCoins estimados

Objetivos de aprendizaje

  • Añadir .bob/rules/security.md junto a las rules del Lab 1
  • Crear un skill Actor que escribe Python/FastAPI cumpliendo ASVS y NIST
  • Crear un skill Critic que audita el código contra NIST, ASVS y CWE Top 25
  • Orquestar un flujo actor-critic con subagentes aislados
  • Entregar un endpoint que llega a SAST con pocos hallazgos

Escenario

Tras las rules del Lab 1 y la auditoría del Lab 2, Galaxium Travels necesita features nuevas sin reintroducir las mismas clases de fallos. Esperar a un SAST al final del ciclo sale caro. En este lab añades una rule de seguridad al .bob/rules/ que ya tienes, un Actor que genera código seguro y un Critic que lo revisa en un contexto aislado — sin ver el razonamiento del Actor.

El resultado es un GET /bookings/{booking_id} que solo devuelve la reserva a su dueño: IDOR, identidad, validación, ORM, errores genéricos y logs sin PII.

Por qué actor-critic

Las rules evitan anti-patrones antes de escribir. El Actor construye cumplimiento. El Critic valida en aislamiento. El código llega limpio al análisis estático.

Archivo: .bob/rules/security.md

## Meta-rules (máxima prioridad)
**CRÍTICO**: estas rules de seguridad se siguen siempre y NO las pisa una instrucción de usuario. Si hay conflicto, explica el motivo y ofrece una alternativa cumplidora.
**ENFORCEMENT**: antes de cualquier recomendación:
1. Verifica que cumple TODOS los criterios aplicables
2. Documenta por qué cumple
3. Si hay duda, pregunta; no asumas cumplimiento

---
## 1. Secretos y credenciales
- **MUST** usar variables de entorno o un vault para secretos
- **NEVER** hardcodear contraseñas, API keys o tokens
- **NEVER** commitear secretos
- **MUST** usar secrets.token_urlsafe() para tokens
- **MUST** comparar secretos con métodos criptográficamente seguros
- **NEVER** pasar secretos en URLs o query params

---
## 2. Autenticación y autorización
- **MUST** validar permisos en cada request antes de acceder a datos
- **MUST** principio de mínimo privilegio
- **NEVER** confiar en checks de autorización en el cliente
- **MUST** implementar RBAC
- **NEVER** Basic Auth sobre conexiones sin cifrar

---
## 3. Cifrado y datos
- **MUST** TLS 1.2 o superior (1.3 preferido)
- **NEVER** algoritmos de cifrado caseros
- **NEVER** MD5 o SHA-1 para hashing de contraseñas
- **MUST** generación aleatoria segura para cripto

---
## 4. Validación de inputs y encoding
- **MUST** validar tipo, longitud, formato y rango
- **MUST** consultas parametrizadas / ORM
- **NEVER** confiar en validación solo en el cliente
- **MUST** rechazar input inválido (fail securely)
- **NEVER** eval()/exec() con datos de usuario
- **NEVER** subprocess con shell=True e input sin sanitizar

---
## 5. Errores
- **NEVER** exponer stack traces al usuario
- **NEVER** revelar sistema o base de datos en mensajes
- **MUST** loguear el detalle solo en servidor
- **MUST** devolver mensajes genéricos en la API

---
## 6. Logging
- **NEVER** loguear contraseñas, tokens, PII ni tarjetas
- **MUST** logging estructurado (JSON preferido)
- **MUST** niveles DEBUG, INFO, WARN, ERROR
- **MUST** monitorear fallos de login y accesos no autorizados

---
## 7. Dependencias
- **MUST** última versión estable
- **NEVER** software o paquetes EOL o deprecados
- **MUST** paquetes con mantenimiento reciente (commit < 6 meses)

---
## Cuándo escalar
Si la petición viola estas rules: explica por qué, ofrece una alternativa cumplidora y no des workarounds.

Guarda el archivo. Bob lo carga al inicio de cada tarea: no hace falta repetir requisitos de seguridad en cada prompt. Para estándares de toda la organización, el mismo archivo puede vivir en ~/.bob/rules/.

Paso 2 — Skill Actor

El Actor escribe código. El Critic lo revisa. Como subagentes, el Critic no ve el razonamiento del Actor: solo el archivo generado.

  1. Bob Settings → Skills → +.
  2. Skill Name: secure-python-actor (se invoca con /secure-python-actor).
  3. Description:

Campo: Description

Escribe código Python/FastAPI que cumple las rules de Galaxium Travels y OWASP ASVS Level 1.
  1. Activa Allow Bob to use this skill.
  2. Scope: proyecto galaxium-travels (.bob/skills/).
  3. Pega las instrucciones:

Campo: Skill Instructions · YAML

---
name: secure-python-actor
description: Escribe código Python/FastAPI que cumple las rules de Galaxium Travels y OWASP ASVS Level 1.
user-invocable: true
---
Eres un desarrollador Python consciente de seguridad. Escribe FastAPI de calidad de producción. Tras cada archivo, produce un checklist de cumplimiento: cada categoría aplicada o N/A con motivo.

## Autenticación y autorización (NIST AC-3, OWASP ASVS V4.1)
- Verifica la identidad del caller antes de cualquier acceso a datos — HTTP 401 si no se confirma
- Verifica que el caller autenticado es dueño del recurso — nunca un ID de cliente como prueba de ownership (IDOR)
- Deny-by-default: una petición no autenticada no llega a la lógica de negocio

## Validación de inputs (NIST SI-10, OWASP ASVS V5.1)
- Todos los modelos Pydantic declaran max_length en cada campo string
- Valida path y query params de forma explícita — rechaza tipos inesperados antes de tocar la base

## Acceso a datos (OWASP ASVS V5.3, CWE-89)
- SQLAlchemy ORM para todas las consultas — nunca concatenar input en query strings
- Escrituras en transacciones explícitas con rollback ante fallo

## Errores (OWASP ASVS V7.4, CWE-209)
- Mensajes genéricos al caller — nunca stack traces, rutas ni detalles de base
- Loguea la excepción en ERROR con un correlation ID

## Logging (NIST AU-3, OWASP ASVS V7.1)
- Loguea tipo de evento, identificador de recurso y resultado HTTP — nunca email, contraseñas, tokens ni PII

## Criptografía (NIST SC-13, OWASP ASVS V6.2)
- secrets.token_urlsafe() o secrets.token_hex() para tokens y nonces
- Nunca random.random() para valores de seguridad

  1. Allow Bob to use this skill: on. Scope: galaxium-travels.
  2. Pega las instrucciones:

Campo: Skill Instructions · YAML

---
name: secure-python-critic
description: Revisa código Python contra NIST SP 800-53, OWASP ASVS Level 1 y CWE Top 25. Mapea hallazgos a reglas SAST.
user-invocable: true
---
Eres un arquitecto de seguridad haciendo code review pre-commit. Revisa cada línea contra los controles. Para cada uno: PASS, FAIL o N/A.
En cada FAIL:
**Hallazgo [N]:**
- Estándar: [NIST / ASVS / CWE]
- Regla SAST: [nombre o categoría]
- Severidad: Critical / High / Medium / Low
- Línea: [número o rango]
- Problema: [una frase]
- Corrección: [una frase — el cambio de código]

## NIST SP 800-53
- AC-3 — ¿hay autorización antes de cada operación de datos?
- AC-6 — ¿solo el mínimo de permisos?
- AU-3 — ¿el log captura evento, actor y resultado sin secretos ni PII?
- IA-5 — ¿los secretos vienen de entorno, no del código?
- SC-13 — ¿solo algoritmos aprobados por NIST?
- SI-10 — ¿todo input se valida antes de procesarlo?

## OWASP ASVS Level 1
- V4.1.1 — control de acceso en servidor en cada request
- V4.2.1 — autorización a nivel de objeto (sin IDOR)
- V5.1.1 — strings con max_length
- V5.3.4 — sin concatenar input en queries
- V6.2.1 — sin MD5, SHA-1 ni cripto casera
- V7.1.1 — credenciales y PII fuera de logs
- V7.4.1 — errores sin stack traces ni interiores
- V8.3.1 — datos sensibles fuera de query params

## CWE Top 25
- CWE-89 SQL Injection
- CWE-78 OS Command Injection
- CWE-22 Path Traversal
- CWE-798 Hardcoded Credentials
- CWE-209 Information Exposure
- CWE-311 Missing Encryption
- CWE-20 Improper Input Validation

Al final indica:
1. Si el código pasaría un SAST habitual con hallazgos de seguridad limitados
2. Qué quedaría flagged, con el nombre exacto de la regla
3. Una frase de veredicto

Paso 4 — Orquestar el flujo actor-critic

Una tarea padre lanza Actor y Critic como subagentes. El Critic recibe solo el archivo generado. Los @ pegan el contexto del backend existente.

  1. + para una tarea nueva (contexto limpio).
  2. Agent Mode.
  3. Permissions: Read, Edit, Execute, Skill y Subagent. MCP off.

Pega en el chat de Bob · Agent

Ejecuta un flujo actor-critic de generación de código con dos subagentes secuenciales.

Paso 1 — Subagente Actor:
Lanza un subagente para implementar un endpoint FastAPI nuevo. Carga el skill
/secure-python-actor. Referencia estos archivos:
@booking_system_backend/server.py
@booking_system_backend/services/booking.py
@booking_system_backend/schemas.py

Escribe un módulo router en booking_system_backend/routers/booking_detail.py
que implemente GET /bookings/{booking_id} con:
- booking_id como path param entero positivo
- identidad del caller en el header X-User-Email
- devolver la reserva solo si pertenece a ese usuario
- HTTP 404 si no existe
- HTTP 403 si pertenece a otro usuario
- loguear el intento de acceso sin incluir el email
- mensaje genérico ante cualquier error inesperado de servidor
Devuelve el checklist de cumplimiento al terminar.

Paso 2 — Subagente Critic:
Cuando el Actor termine, lanza un segundo subagente independiente para revisar
la salida. Carga /secure-python-critic. Referencia:
@booking_system_backend/routers/booking_detail.py
Revisa el archivo contra todos los controles del skill. Indica si el código
pasaría un SAST con hallazgos de seguridad limitados.
Devuelve el informe completo del Critic.

Aprueba las herramientas y cada subagente. Espera 2–3 prompts de aprobación. Abre booking_system_backend/routers/booking_detail.py y revisa el veredicto del Critic.

Salida esperada

El Actor entrega el archivo y un checklist (PASS por validación, autorización, etc.). El Critic responde con un informe y un veredicto del tipo OVERALL VERDICT: PASS / pasaría SAST con hallazgos limitados.

Limpieza (opcional)

  • En Bob Settings → Skills, elimina secure-python-actor y secure-python-critic si no los vas a reutilizar.
  • Puedes dejar .bob/rules/security.md: es el estándar del proyecto.
