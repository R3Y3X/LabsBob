Step 1. Crear el tópico inventory.transactions

Necesitamos un canal central donde fluirán todas las transacciones de inventario antes de que ksqlDB las procese.

El script sube el código a la VM via SSH, lanza un Kubernetes Job y crea el tópico desde dentro del cluster.

  1. Abre una terminal y navega al lab: 
    cd Labs-tech-summit/Lab1/inventory-pipeline
  2. Ejecuta el paso 1:
./setup.sh -s 1

✓ Checkpoint

  • El output termina con Created topic 'inventory.transactions'
  • Línea final: OK: create_topic

El script ejecuta create_topic.py dentro de un pod python:3.11-slim en el namespace confluent. Configura:

  • 1 partición — mantiene el orden de los eventos determinístico.
  • Replicación 3 — alta disponibilidad con los 3 brokers del cluster.
  • retention.ms = -1 — retención infinita para que los agentes puedan consultar el histórico completo.

Si el tópico ya existe, el script lo detecta y lo omite sin error.

Crea el tópico manualmente desde la interfaz de Confluent Cloud.

  1. Inicia sesión en confluent.cloud y selecciona tu cluster.
  2. En el menú lateral, haz clic en Topics → Add topic.
  3. Nombre: inventory.transactions · Partitions: 1 · haz clic en Create with defaults.
  4. Ve a la pestaña Configuration → Edit Settings → cambia Retention Time a infinite → Save changes.

✓ Checkpoint

  • El tópico inventory.transactions aparece en la lista con status Active.
  • Configuration muestra Retention Time = Infinite.

Step 2. Crear el tópico derivado inventory.availability

Un tópico derivado calcula disponibilidad por SKU/sucursal en tiempo real, sin que los agentes tengan que sumar transacciones ellos mismos.

El script ejecuta dos sentencias SQL contra el endpoint interno de ksqlDB mediante la API REST.

  1. Ejecuta el paso 2:
./setup.sh -s 2

✓ Checkpoint

  • currentStatus: SUCCESS (Stream created)
  • currentStatus: SUCCESS (Created query with ID CTAS_INVENTORY_AVAILABILITY_1)
  • Línea final: OK: create_derived_topic
CREATE STREAM IF NOT EXISTS inventory_transactions (
  sku VARCHAR,
  branch VARCHAR,
  quantity INT
) WITH (
  KAFKA_TOPIC='inventory.transactions',
  KEY_FORMAT='KAFKA',
  VALUE_FORMAT='JSON'
);
CREATE TABLE IF NOT EXISTS inventory_availability WITH (
  KAFKA_TOPIC='inventory.availability',
  KEY_FORMAT='JSON',
  VALUE_FORMAT='JSON',
  PARTITIONS=1
) AS
SELECT
  sku,
  branch,
  SUM(quantity) AS available_quantity
FROM inventory_transactions
GROUP BY sku, branch
EMIT CHANGES;

Las decisiones de configuración de este lab están pensadas para el caso de uso específico de agentes de IA consultando un histórico de inventario:

  • 1 partición — orden determinístico: Con una sola partición, Kafka garantiza que los mensajes se consumen exactamente en el orden en que fueron producidos. Esto es crítico para el cálculo correcto de disponibilidad (sumas y restas de stock). Con 3 particiones los mensajes se distribuyen entre particiones y el orden global entre ellas no está garantizado.
  • Retención infinita (retention.ms = -1) — histórico para agentes: Los agentes de IA del Lab 2 necesitan consultar el historial completo de transacciones para calcular el stock actual desde el inicio. Con retención limitada (p. ej. 1 día con cleanup.policy=delete), los eventos más antiguos desaparecerían y los cálculos serían incorrectos.
  • ¿Cuándo usarías 3 particiones? En producción con alto throughput (miles de transacciones por segundo), donde múltiples consumidores procesan en paralelo y el orden global no importa. El paralelismo mejora la velocidad de procesamiento a cambio de perder el orden estricto entre particiones.
  • ¿Cuándo usarías cleanup.policy=delete con 1 día? En workshops efímeros o pipelines de telemetría donde solo importa el dato reciente, los eventos tienen corta vida útil y el almacenamiento del disco del servidor es limitado.
  1. En el menú lateral, haz clic en ksqlDB → selecciona el cluster activo.
  2. Ve a Streams → Create in Editor.
  3. Pega y ejecuta (Run Query):

  quantity INT

  VALUE_FORMAT='JSON'
