Lab 06 — Revisión y ajustes

4–8 BobCoins
~20 minutos

Ya tienes una tienda funcionando y animada. La fase de revisión pone la aplicación al lado del diseño, cierra las diferencias en una sola pasada y verifica que se sostenga más allá del camino feliz.

Lo que vas a hacer

  • (Opcional) Hacer que Bob revise las tres pantallas contra los mockups y aplique las correcciones.
  • Verificar responsividad, accesibilidad y casos borde.
  • Reflexionar sobre el flujo de trabajo de mockup a aplicación.

Antes de empezar

Labs 02–05 completos: las tres pantallas están construidas y animadas, y la aplicación corre.

Paso 1 — (Opcional) Revisa las tres pantallas contra los mockups

Opcional

Si tus pantallas ya coinciden bastante con los mockups después de los Labs 02–05, puedes saltar al paso 3 (Verifica la responsividad). Ejecuta esta revisión cuando quieras que Bob detecte las diferencias visuales más finas.

Cambia Bob a Plan Mode para que revise sin editar. Adjunta las tres capturas — mockups/home.png, mockups/product.png y mockups/cart.png — al chat de Bob y después ejecuta un único análisis.

Adjunto los tres mockups de diseño de esta aplicación (home, product, cart). Compará cada
uno con cómo se renderiza actualmente la página correspondiente (src/pages/Home.jsx,
src/pages/Product.jsx, src/pages/Cart.jsx y src/components/ProductCard.jsx).

Producí UNA sola checklist consolidada y concreta de las diferencias visuales que
encuentres, agrupadas por pantalla: espaciado, tamaños, colores, alineación, elementos
faltantes o sobrantes. Sé específico (qué elemento, qué debería cambiar).

Los textos de la UI están en inglés a propósito, igual que los mockups: no los reportes
como diferencias ni propongas traducirlos.

No cambies código todavía.

Haz que la lista sea accionable

Si Bob es vago ("mejorar el espaciado"), insiste: "Sé específico — qué elemento y qué valor debería cambiar." Quieres una checklist verificable, no opiniones.

Paso 2 — (Opcional) Aplica las correcciones

Si ejecutaste la revisión anterior, cambia a Agent Mode y haz que Bob trabaje toda la checklist en una pasada guiada.

Recorre la checklist que acabas de producir y aplica las correcciones en Home.jsx,
ProductCard.jsx, Product.jsx y Cart.jsx para que cada pantalla coincida con su mockup.
Haz los cambios en lotes chicos y dime qué cambiaste en cada lote, así puedo ir
verificando en el navegador.

Mantén todos los textos de la UI en inglés. No toques src/api/client.js.

Mira el navegador después de cada lote y ve tachando ítems de la lista.

Paso 3 — Verifica la responsividad

Redimensiona el navegador (o usa la barra de dispositivos en las herramientas de desarrollo) hasta el ancho de un teléfono.

Asegúrate de que las tres pantallas sean responsive: la grilla de productos se reduce a
menos columnas, el detalle de producto pasa de dos columnas a apilado, y el carrito apila
el resumen debajo de los artículos en pantallas chicas. Corrige cualquier layout que se
desborde o se superponga.

Mantén todos los textos de la UI en inglés.

Paso 4 — Pasada rápida de accesibilidad y casos borde

Haz una revisión rápida de accesibilidad y robustez sobre las tres pantallas:
- Cada imagen de producto tiene un alt significativo (el nombre del producto).
- Los botones y links son elementos <button>/<a> reales con etiquetas discernibles.
- Los selectores de cantidad y los botones "Add to cart" / "Place order" son enfocables
  por teclado.
- Los estados de carga, carrito vacío y "product not found" se renderizan sin errores.
Lista qué cambiaste.

Mantén todos los textos de la UI en inglés.

Después prueba tú mismo los casos borde:

  • El carrito vacío muestra el estado vacío, no un resumen roto.
  • El producto sin stock (GrindPro Burr Grinder) se renderiza correctamente.
  • Una llamada a la API lenta o fallida muestra un mensaje amable, no una pantalla en blanco.
  • Hacer un pedido desde un carrito con ítems muestra la confirmación y vacía el carrito.

Paso 5 — (Opcional) Compila para producción

Confirma que la aplicación compila sin errores:

npm run build
npm run preview

npm run build debería terminar sin errores, y la vista previa debería comportarse igual que el servidor de desarrollo. Este es el artefacto que desplegarías en cualquier hosting estático.

Reflexión

Toma distancia y mira cómo fue el ciclo de vida con Bob:

FaseQué hiciste
PlanificarConvertiste mockups + un contrato de API en un plan pantalla por pantalla, antes de escribir código.
ConstruirImplementaste una pantalla a la vez a partir de una captura, contra una API y un sistema de diseño fijos.
PulirAgregaste movimiento para que la tienda se sintiera viva.
RevisarComparaste contra el diseño en una sola pasada y reforzaste los estados.

Preguntas para debatir

  • ¿Dónde ayudó el esqueleto preconstruido (cliente, carrito, toast, tokens) a mantener a Bob en el camino?
  • ¿Dónde ser específico en un prompt produjo un mejor resultado que ser vago?
  • Si mañana se suma alguien nuevo al equipo, ¿qué necesitaría tener documentado primero? (Eso es el Lab 07.)

Criterios de éxito

  • (Opcional) Las tres pantallas revisadas contra sus mockups y las diferencias aplicadas.
  • Las tres pantallas son responsive.
  • Accesibilidad y casos borde (vacío, error, sin stock) contemplados.
  • npm run build termina con éxito.
