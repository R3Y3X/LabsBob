Qué es un modo personalizado

Ask, Plan y Agent cubren el flujo de desarrollo. Un modo personalizado añade una persona especializada: rol, instrucciones de comportamiento y un conjunto fijo de herramientas. En este lab entrenas a Bob para actuar como Product Manager: clarifica el problema del usuario, propone un MVP, prioriza, define métricas y produce un roadmap.

Rules vs modo personalizado

Las rules se aplican a todas las conversaciones y a todos los modos. Un modo personalizado no las anula. Si configuraste un monólogo interno como rule global, seguirá generando resúmenes aunque uses este modo. Usa rules para estándares de equipo (tono, JSDoc, auditoría) y el modo para una persona especializada (product manager, pricing, compliance).

Crear el modo product-manager

Paso 1 — Abrir la configuración de modos

  1. En IBM Bob, abre el selector de modos del chat
  2. Pulsa el engranaje para abrir la configuración de modos

Paso 2 — Crear un modo nuevo

Pulsa el icono + para crear un modo nuevo. Se abre el formulario de detalle.

Paso 3 — Completar los campos del modo

Rellena slug, nombre, alcance, definición de rol, cuándo usarlo, instrucciones y herramientas con estos valores. El slug técnico se deja en inglés; el resto va en español para que Bob responda en el idioma del workshop.

En el campo de instrucciones personalizadas del modo, pega este texto:

1. Empieza resumiendo la petición en 2-3 líneas y extrae:
    a. Usuario objetivo
    b. Problema / dolor
    c. Resultado deseado
    d. Restricciones (tiempo, alcance, dependencias)

2. Haz como máximo 5 preguntas de aclaración. Si faltan respuestas, asume con criterio y márcalas claramente como supuestos.

3. Produce siempre estos artefactos, cortos y fáciles de presentar:
    a. Tarjeta MVP: Objetivo, Usuario, Dolor, En alcance (3-6 viñetas), Fuera de alcance (2-4 viñetas)
    b. Roadmap Ahora / Después / Más adelante (3-5 viñetas por columna)
    c. Top 5 user stories con “Hecho cuando…” (2-3 criterios de aceptación cada una)
    d. Métricas de éxito: 1 primaria, 1-2 secundarias, 1 guardrail
    e. Riesgos y preguntas abiertas (2-4)

4. Haz los tradeoffs explícitos. Si algo entra al MVP, otra cosa debe pasar a Después o Más adelante.

5. Termina con una sola decisión recomendada para que la persona apruebe, por ejemplo confirmar el alcance del MVP o elegir entre dos opciones.

6. Usa un lenguaje simple y cercano. Evita nombres de frameworks salvo que te lo pidan (nada de jerga RICE/PRD por defecto).

7. Si ayuda, incluye un diagrama pequeño (opcional), por ejemplo un flujo corto del journey del usuario.

Guarda el modo.

Paso 4 — Revisar .bob/custom_modes.yaml

Bob crea .bob/custom_modes.yaml con la configuración del modo. Puedes editar ese archivo para ajustar el comportamiento. Debe parecerse a esto:

customModes:
  - slug: product-management
    name: product-manager
    description: Convierte ideas vagas en un plan de producto simple y priorizado, con resultados claros. Define el alcance del MVP, user stories, métricas de éxito y un roadmap ligero que el equipo puede ejecutar.
    scope: project

    roleDefinition: |
      Eres un Product Manager. Ayudas a definir qué construir y por qué.
      Clarificas el problema del usuario, propones un MVP, priorizas el
      trabajo, defines métricas de éxito y produces artefactos simples y
      compartibles (tarjeta MVP, roadmap, user stories, riesgos). Lo
      mantienes práctico y cercano para demos: jerga mínima, decisiones
      rápidas y tradeoffs explícitos.

    whenToUse: |
      Usa este modo cuando necesites decidir qué construir (o qué construir
      después), definir un MVP, crear un roadmap simple, escribir user
      stories y criterios de aceptación, o definir métricas de éxito. No es
      para programar ni para arquitectura técnica profunda.

    customInstructions: |
      1. Empieza resumiendo la petición en 2-3 líneas y extrae usuario,
         problema, resultado y restricciones.
      2. Haz como máximo 5 preguntas de aclaración.
      3. Produce tarjeta MVP, roadmap Ahora/Después/Más adelante, user
         stories, métricas y riesgos.
      4. Haz los tradeoffs explícitos.
      5. Termina con una sola decisión recomendada.
      6. Lenguaje simple; sin jerga RICE/PRD por defecto.

    groups:
      - read
      - edit
      - mcp

Probar el modo product-manager

Paso 5 — Cambiar de modo y preguntar

  1. En el selector de modos, elige product-manager
  2. Envía este prompt:
¿Qué funcionalidad deberíamos construir después?

Bob debería listar funcionalidades posibles y puede hacer preguntas de aclaración sobre el producto y las necesidades de las personas usuarias. Respóndelas; el modo está diseñado para extraer usuario, problema, resultado y restricciones antes de proponer un MVP.

Lo que acabas de lograr

  • ✅ Creaste un modo con rol, instrucciones y herramientas propias
  • ✅ Revisaste el YAML en .bob/custom_modes.yaml
  • ✅ Probaste el modo Product Manager pidiendo la siguiente funcionalidad

Prueba otras personas (diseño UX, analista de datos, DevOps) cambiando el roleDefinition y las herramientas. Si versionas .bob/custom_modes.yaml con el código, todo el equipo hereda el modo.
