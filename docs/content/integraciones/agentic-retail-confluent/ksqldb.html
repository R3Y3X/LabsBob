Qué hace el stream: envuelve el tópico inventory.transactions como una vista SQL (incluye los campos del schema de transacciones).

Mensaje esperado de Bob — CREATE STREAM (no lo copies al chat)

CREATE STREAM IF NOT EXISTS INVENTORY_TRANSACTIONS (
  sku VARCHAR,
  branch VARCHAR,
  quantity INT,
  transaction_type VARCHAR,
  timestamp VARCHAR,
  source VARCHAR,
  reference VARCHAR
) WITH (
  KAFKA_TOPIC='inventory.transactions',
  KEY_FORMAT='KAFKA',
  VALUE_FORMAT='JSON_SR'
);

Pestaña Flow — panel CREATE TABLE: Control Center recorta el statement a la derecha. Lo que ves al seleccionar el nodo se parece a esto (puede cortar GROUP BY / EMIT CHANGES).

Mensaje esperado en Flow — CREATE TABLE recortado (no lo copies al chat)

CREATE TABLE IF NOT EXISTS INVENTORY_AVAILABILITY WITH (CLEANUP_POLICY='compact', KAFKA_TOPIC='inventory.availability', KEY_FORMAT='JSON', PARTITIONS=1, REPLICAS=3, RETENTION_MS=-1, VALUE_FORMAT='JSON_SR') AS SELECT
  INVENTORY_TRANSACTIONS.SKU SKU,
  INVENTORY_TRANSACTIONS.BRANCH BRANCH,
  SUM(INVENTORY_TRANSACTIONS.QUANTITY) AVAILABLE_QUANTITY
FROM INVENTORY_TRANSACTIONS INVENTORY_TRANSACTIONS

Pestaña Persistent queries — statement completo: misma tabla, con GROUP BY y EMIT CHANGES. El resultado se escribe en inventory.availability.

Mensaje esperado en Persistent queries — CREATE TABLE completo (no lo copies al chat)

CREATE TABLE IF NOT EXISTS INVENTORY_AVAILABILITY WITH (CLEANUP_POLICY='compact', KAFKA_TOPIC='inventory.availability', KEY_FORMAT='JSON', PARTITIONS=1, REPLICAS=3, RETENTION_MS=-1, VALUE_FORMAT='JSON_SR') AS SELECT
  INVENTORY_TRANSACTIONS.SKU SKU,
  INVENTORY_TRANSACTIONS.BRANCH BRANCH,
  SUM(INVENTORY_TRANSACTIONS.QUANTITY) AVAILABLE_QUANTITY
FROM INVENTORY_TRANSACTIONS INVENTORY_TRANSACTIONS
GROUP BY INVENTORY_TRANSACTIONS.SKU, INVENTORY_TRANSACTIONS.BRANCH
EMIT CHANGES;

¿Por qué EMIT CHANGES?

Le indica a ksqlDB que el resultado es un streaming continuo — cada nueva transacción recalcula y publica el stock actualizado de ese SKU/sucursal. Sin EMIT CHANGES sería una consulta de una sola vez.

SQL que debe imprimir Bob (contrástalo; no lo pegues otra vez)

El INSERT agrupa por SKU/sucursal sobre la tabla de catálogo del tópico fuente y escribe en inventory.availability.flink. El conector es confluent; el Kafka y Schema Registry ya están en el catálogo. Nombres de tópico ya personalizados en pantalla.

Mensaje esperado de Bob — Flink CMF (no lo copies al chat)

CREATE TABLE IF NOT EXISTS `flink-catalog`.`flink-database`.`inventory.availability.flink` (
  SKU STRING, BRANCH STRING, AVAILABLE_QUANTITY BIGINT,
  PRIMARY KEY (SKU, BRANCH) NOT ENFORCED
) WITH (
  'connector' = 'confluent',
  'kafka.retention.time' = '0',
  'key.format' = 'json-registry',
  'value.format' = 'json-registry',
  'changelog.mode' = 'upsert'
);

INSERT INTO `flink-catalog`.`flink-database`.`inventory.availability.flink`
SELECT SKU, BRANCH, SUM(CAST(QUANTITY AS BIGINT)) AS AVAILABLE_QUANTITY
FROM `flink-catalog`.`flink-database`.`inventory.transactions`
WHERE SKU IS NOT NULL AND BRANCH IS NOT NULL
GROUP BY SKU, BRANCH;

  • ksqlDB — ideal para agregaciones simples, filtros y joins sobre streams de Kafka con sintaxis SQL familiar. Perfecto para este track: calcular stock disponible en tiempo real con pocas líneas.
  • Apache Flink — recomendado cuando necesitas ventanas de tiempo (tumbling, sliding), joins complejos entre múltiples streams, detección de patrones (CEP) o procesamiento con estado avanzado. Escala mejor en producción con alto throughput.
  • En este workshop no comparten tópico: ksqlDB escribe en inventory.availability (pipeline principal / Track F) y Flink en inventory.availability.flink (extensión pedagógica). Mismo cálculo, sinks distintos.
