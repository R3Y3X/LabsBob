Step 1. Crear el tópico inventory.transactions

Necesitamos un canal central donde fluirán todas las transacciones de inventario antes de que ksqlDB las procese. Bob ya tiene SSH y los tres .env desde el Paso 0 — el que cuenta para setup.sh es el de la raíz del bundle. En Windows el SSH del Paso 0 fue ssh.exe; este step usa Git Bash para ./setup.sh -s 1.

¿Cómo funciona internamente?

setup.sh -s 1 entra a la VM vía SSH y lanza dos Jobs en el namespace confluent: create_topic.py y después register_schema.py (subject inventory.transactions-value, JSON Schema). Parámetros del tópico:

  • 1 partición — orden de eventos determinístico, crítico para el cálculo de stock.
  • Replicación 3 — alta disponibilidad con los 3 brokers del cluster.
  • retention.ms = -1 — retención infinita para que los agentes consulten el histórico completo.
  • Si el tópico o el schema ya existen, los scripts lo detectan y lo omiten sin error.

Step 2. Crear la tabla derivada inventory.availability

ksqlDB calcula disponibilidad por SKU/sucursal en tiempo real y publica el resultado como JSON_SR. El nombre del tópico y de la tabla ya está aislado con tu workspace.

¿Qué hace setup.sh -s 2 internamente?

Ejecuta el Step 2 desde dentro de la VM:

  • 0. ensure_ksql_sr — si el servidor ksql no tiene ksql.schema.registry.url, parchea el ConfigMap y reinicia ksql (idempotente: si ya está, imprime KSQL_SR_OK y no toca nada).
  • 1. Stream y tabla vía ksqlDB — crea los objetos con nombres de workspace y agrega disponibilidad por SKU y sucursal.
  • 2. Contrato JSON_SR — ksqlDB reutiliza el schema registrado para el tópico fuente y serializa el resultado derivado.

Las decisiones de configuración de este lab están pensadas para el caso de uso específico de agentes de IA consultando un histórico de inventario:

  • 1 partición — orden determinístico: Con una sola partición, Kafka garantiza que los mensajes se consumen exactamente en el orden en que fueron producidos. Esto es crítico para el cálculo correcto de disponibilidad (sumas y restas de stock). Con 3 particiones los mensajes se distribuyen entre particiones y el orden global entre ellas no está garantizado.
  • Retención infinita (retention.ms = -1) — histórico para agentes: Los agentes de IA del Track F necesitan consultar el historial completo de transacciones para calcular el stock actual desde el inicio. Con retención limitada (p. ej. 1 día con cleanup.policy=delete), los eventos más antiguos desaparecerían y los cálculos serían incorrectos.
  • ¿Cuándo usarías 3 particiones? En producción con alto throughput (miles de transacciones por segundo), donde múltiples consumidores procesan en paralelo y el orden global no importa. El paralelismo mejora la velocidad de procesamiento a cambio de perder el orden estricto entre particiones.
  • ¿Cuándo usarías cleanup.policy=delete con 1 día? En workshops efímeros o pipelines de telemetría donde solo importa el dato reciente, los eventos tienen corta vida útil y el almacenamiento del disco del servidor es limitado.

🎯 Propósito — Por qué estas decisiones importan en producción

En un sistema de inventario real para Voltia, estas son las tradeoffs clave a evaluar:

  • 3 particiones + cleanup.policy=delete (1 día): Correcto cuando el sistema de inventario procesa miles de transacciones por segundo de múltiples tiendas simultáneamente, múltiples consumidores leen en paralelo y el almacenamiento del servidor es limitado. Los eventos más recientes son suficientes para decisiones operativas inmediatas.
  • 1 partición + retención infinita (este lab): Correcto cuando los agentes de IA necesitan reconstruir el estado completo del inventario desde el primer evento, el orden cronológico garantiza que cada transacción sea procesada en la secuencia exacta en que ocurrió, y la consistencia del cálculo de stock importa más que el throughput.
  • Factor de replicación 3: el cluster TechZone tiene 3 brokers; TOPIC_REPLICATION_FACTOR=3 ya viene en el .env. No lo bajes a 1.

CREATE STREAM IF NOT EXISTS INVENTORY_TRANSACTIONS (
  sku VARCHAR,
  branch VARCHAR,
  quantity INT,
  transaction_type VARCHAR,
  timestamp VARCHAR,
  source VARCHAR,
  reference VARCHAR
) WITH (
  KAFKA_TOPIC='inventory.transactions',
  KEY_FORMAT='KAFKA',
  VALUE_FORMAT='JSON_SR'
);
  1. Pega y ejecuta (Run Query):
CREATE TABLE IF NOT EXISTS INVENTORY_AVAILABILITY WITH (
  KAFKA_TOPIC='inventory.availability',
  KEY_FORMAT='JSON',
  VALUE_FORMAT='JSON_SR',
  PARTITIONS=1,
  REPLICAS=3
) AS
SELECT
  sku,
  branch,
  SUM(quantity) AS available_quantity
FROM INVENTORY_TRANSACTIONS
GROUP BY sku, branch
EMIT CHANGES;
