Problemas de migración esperados y respuestas
#Problema que plantea BobTu respuesta
1 Javassist charset warning — "Avoid using default charset when the output stream is a PrintStream" Aprobar, fijado a 3.29.2-GA — ver advertencia abajo
2 OGNL SecurityManager conflict — "The default value of the java.security.manager system property has been changed to disallow" Rechazar — es un falso positivo

Javassist: insiste en 3.29.2-GA — Bob puede proponer otra versión

Bob suele proponer una javassist más nueva (por ejemplo 3.30.2-GA) y ofrecer 3.29.2-GA como segunda opción, formulada como rechazo:

Yes, upgrade javassist to 3.30.2-GA
No, use 3.29.2-GA instead

Elige 3.29.2-GA. Es la versión con la que este workshop está construido y probado, y la que snapB/snapC ya fijan. Ambas versiones son compatibles con Java 8, así que una más nueva no romperá tu build hoy — pero mantén todo el grupo en una sola versión.

Lo que hagas, no omitas el cambio por completo — eso deja el finding sin resolver.

Por qué el finding de OGNL es un falso positivo — vale dos minutos

El pom.xml de snapA ya fija ognl a 3.1.26 para compatibilidad con Struts 2.5.30, y lo dice en un comentario justo encima de la dependencia. La clase OgnlSecurityManager marcada existe en todas las versiones OGNL disponibles (3.1.26–3.4.11), así que actualizar no la eliminaría. La llamada solo lanza excepción en runtime en Java 18+ cuando hay un SecurityManager no nulo instalado — cosa que Liberty nunca hace.

El escáner tiene razón en que el código existe, y está completamente equivocado en que importe aquí. Rechazar es la respuesta correcta — y es el momento más transferible del lab: que un finding sea real y que sea relevante para tu runtime son dos preguntas distintas, y solo tú puedes responder la segunda.

El finding de javassist también es menos urgente de lo que parece

Bob probablemente citará JEP 400 y "Java 17+" como razón. Ten en cuenta que el Lab 1 se queda en Java 8 — el charset por defecto no cambió a UTF-8 hasta Java 18, así que el bug que describe no puede afectarte en este lab. AMA lo marca porque planifica para un destino Liberty que podría correr en una JVM más nueva.

Aprobar sigue siendo correcto (es inofensivo y es real), solo no dejes que el encuadre de "desajustes silenciosos de charset" convenza a la sala de que esquivaron un bug activo.

Checkpoint — cómo se ve un replatforming terminado

  • pom.xml tiene el io.openliberty.tools:liberty-maven-plugin
  • src/main/liberty/config/server.xml existe, con la app simple-pharmacy.war y las features de Liberty
  • maven.compiler.source/target siguen en 1.8, y el código sigue importando javax.servlet.* — el Lab 1 no cambia ni la versión de Java ni el namespace
  • mvn clean compile → BUILD SUCCESS

¿Quieres ejecutarla? Puedes — pero no es obligatorio

Ya viste la aplicación en la demo de apertura, así que ejecutarla no es requisito para terminar este lab — una compilación limpia basta. Si quieres verla en Liberty de todos modos, puedes hacerlo. Si algo falla, copia el error — de la terminal o del navegador — al chat de Bob y pídele que lo arregle. Depurar su propia migración a partir del texto del error es exactamente para lo que sirve Agent Mode.

Libera el puerto antes del siguiente lab

Si Bob o tú arrancasteis un servidor Liberty, deténlo para que el Lab 2 no quede bloqueado:

  • macOS / Linux: pulsa Ctrl+C en la terminal donde corre Liberty. Si el puerto sigue ocupado: lsof -ti:9080 | xargs kill -9
  • Windows (PowerShell): pulsa Ctrl+C; si el puerto sigue ocupado, ejecuta mvn liberty:stop, o netstat -ano | findstr :9080 y luego taskkill /PID <pid> /F
Solución de problemas y ayuda

Solución de problemas

mvn: command not found tras instalar Maven

  • Confirma que Maven está instalado: mvn --version. En macOS/Linux (SDKMAN!) comprueba sdk version y reinstala con sdk install maven; en Windows reinstala con winget install Apache.Maven
  • Reinicia tu IDE / Bob por completo y abre una terminal nueva para que se tome el PATH actualizado
  • Verifica de nuevo: mvn --version

La terminal de Bob usa la versión de Java equivocada

sdk use java solo aplica a la shell donde se ejecutó — la terminal de Bob es una shell separada. Ejecútalo en la terminal de Bob específicamente:

sdk use java 8.0.492-zulu

O establece el default global para que cada shell nueva lo tome:

sdk default java 8.0.492-zulu

Bob no puede leer archivos del proyecto (I cannot access that file / File not found)

  • Verifica que abriste la subcarpeta snapA-java-liberty-replatforming como raíz del proyecto — no la carpeta padre lab1-*
  • Comprueba permisos de archivos: ls -la
  • Asegúrate de que Bob tiene acceso de lectura al workspace
  • Prueba referenciar archivos con la sintaxis @filename

Unable to access jarfile al proporcionar la ruta del ZIP AMA

El error se parece a:

Error: Unable to access jarfile /Applications/IBM Bob.app/Contents/Resources/app/extensions/bob-code/assets/jars/ta-jam-2.2.1.jar

A Bob le faltan los JARs de tooling AMA. Vienen con este workshop — descarga jars.zip (51 MB) desde los materiales del workshop y:

  • Crea una carpeta jars dentro del bundle de la app Bob en /Applications/IBM Bob.app/Contents/Resources/app/extensions/bob-code/assets
  • Descomprime jars.zip ahí para que la estructura sea: 
    ├── jars/
│   └── prompt-lib/
│       ├── prompt-lib-2.2.0.jar
│   └── ta-jam-2.2.1.jar
  • Cierra y reinicia Bob

Ejecuta Bob desde /Applications, no desde /Volumes

Asegúrate de que Bob no se ejecuta desde /Volumes (un .dmg montado). Mueve la app IBM Bob a /Applications y ejecútala desde ahí; de lo contrario macOS no le permitirá crear carpetas ni colocar archivos .jar dentro del bundle.

SRVE0321E: The [struts2] filter did not load during start up

Seguro ignorar. La app migrada funciona correctamente — refleja un efecto secundario de class-loading que no afecta el comportamiento en runtime.

CWWKS9660E: The orb element with the defaultOrb id attribute requires a user registry

Seguro ignorar, siempre que la app no use componentes EJB basados en ORB — y esta no los usa.

Build falla con invalid target release: 21 / Bob dice "Java 21 is not available"

El recipeConfig/rewrite.yml del migration plan lista recetas OpenRewrite de upgrade Java (Java8toJava11, UpgradeToJava17, UpgradeToJava21). Esas pertenecen al Lab 2 — el Lab 1 se queda en Java 8 con el namespace javax.*. Si se aplican, pom.xml salta a Java 21 y el compilador Java 8 no puede apuntar a un release más nuevo.

Esto es deriva de recetas, no un JDK faltante — no instales ni cambies a Java 21 aquí. Revierte el pom a Java 8:

  • Establece maven.compiler.source/target y el maven-compiler-plugin <source>/<target> de vuelta a 1.8
  • Mantén el namespace javax.*

O pídeselo a Bob:

Este es el Lab 1 (solo replatforming Liberty). Revierte pom.xml a Java 1.8 (los cuatro marcadores),
mantén el namespace javax.*, y elimina cualquier bump de javassist/asm más allá del fix aprobado.
NO apliques las recetas Java 8→11/17/21 — eso es el Lab 2.

Luego recompila con mvn clean package.

Build falla con Unsupported class file major version

Maven corre en un JDK más nuevo que 8. El Lab 1 se queda en Java 8 — apunta Maven a él.

  • macOS / Linux (SDKMAN!): sdk use java 8.0.492-zulu
  • Windows: establece JAVA_HOME a tu carpeta Temurin 8 y reabre la terminal — o ejecuta sdk use java 8.0.492-zulu si instalaste vía SDKMAN! en Git Bash/WSL

Luego recompila:

mvn clean package

Confirma con mvn --version (imprime la versión de Java que usa Maven, que puede diferir del java -version de tu shell).

Bob propone un cambio y no estás seguro

Siempre que Bob ofrezca "show me the exact edits before applying them", acéptalo — Bob renderiza el diff completo para revisión antes de tocar archivos. También puedes hacerle una pregunta de seguimiento en el chat; Bob espera.

Address already in use / el puerto no se libera tras Ctrl+C

Una ejecución anterior de Liberty sigue reteniéndolo.

  • macOS / Linux: lsof -ti:9080,9443 | xargs kill -9
  • Windows (PowerShell): mvn liberty:stop. Si el puerto sigue ocupado: netstat -ano | findstr :9080, luego taskkill /PID <pid> /F

No ignores este — hace que cada fix posterior parezca roto

Si el puerto está tomado, tu servidor nuevo nunca lo enlaza y el antiguo sigue respondiendo. Editarás archivos, recompilarás, reiniciarás y no verás ningún cambio — porque sigues hablando con el servidor obsoleto. Cada vez que un fix "no hace nada", comprueba primero si hay un Liberty suelto.
