Caso de uso: migrar de Traditional WebSphere a Liberty

La aplicación se ejecuta actualmente en:

  • Servidor de aplicaciones : WebSphere Application Server (TWas)
  • Versión Java : 8
  • Interfaz : Struts

Lo migrarás a:

  • Servidor de aplicaciones : Liberty Application Server
  • Versión de Java : 8 (sin cambios; consulte el Laboratorio 2 para conocer la actualización de la versión)
  • Interfaz : Struts (sin cambios; consulte el Laboratorio 3 para conocer la migración de la interfaz de usuario)

Por qué esto importa

  • WebSphere Application Server (TWas) es un servidor Java empresarial tradicional y pesado.
  • Liberty es el sucesor moderno, liviano, modular y compatible con la nube: inicio más rápido, espacio más pequeño y compatible con contenedores.

Bob puede instalar Java 8 por ti

Si falta Java 8, el flujo de trabajo lo instala a través de SDKMAN! por sí solo. Para un taller cronometrado, es aún más rápido tenerlo listo desde el principio, por lo que vale la pena seguir los pasos a continuación de todos modos. Maven, sin embargo, debes instalarlo tú mismo.

La forma más sencilla es SDKMAN! , una herramienta que instala y cambia entre versiones de Java por ti.

              sdk default java 8.0.504+1-zulu

              sdk install maven

Opción A — Winget (permanece en PowerShell, la más simple). winget es el instalador de la aplicación integrado en Windows 10/11. Ejecuta cada línea en PowerShell : 

              winget install EclipseAdoptium.Temurin.8.JDK

Luego, cierra y vuelve a abrir PowerShell para que se encuentren los nuevos comandos java y mvn .

Opción B — SDKMAN! en Git Bash o WSL (idéntico a macOS/Linux). SDKMAN! hace que cambiar entre Java 8 y Java 21 (necesitará 21 del Laboratorio 2 en adelante) sea de una sola línea, pero necesita un shell estilo Linux:

  • Git Bash viene con Git para Windows .
  • WSL es el entorno Linux integrado: ejecuta wsl --install en un PowerShell de administrador y luego vuelve a abrir.

Abre Git Bash o WSL y ejecuta los comandos macOS/Linux desde las otras pestañas. Sigue usando el mismo shell para cada comando sdk , java y mvn en esta práctica de laboratorio.

Ahora verifica: estas comprobaciones son las mismas en todos los sistemas operativos:

        java -version

Debería ver una versión que comience con 1.8. , p. openjdk version "1.8.0_504" de Zulu (el número de parche exacto no importa; la parte clave es 1.8 = Java 8). 

        mvn --version

mvn --version muestra el Java con el que Maven construirá

Esto puede diferir del valor predeterminado de tu shell java -version : Maven sigue a JAVA_HOME (o, con SDKMAN!, la instalación activa). Para el Laboratorio 1, ambos deben informar Java 8 . En Windows, apunta JAVA_HOME a la carpeta Temurin 8 (por ejemplo, C:\Program Files\Eclipse Adoptium\jdk-8… ) si Maven elige la carpeta equivocada.

Otras formas de instalar Java 8 (y Apple Silicon gotcha)

En Macs Apple Silicon (serie M) , Eclipse Temurin/Adoptium tiene no compilación Java 8; los identificadores obsoletos como 8.0.432-tem fallarán con "no disponible". Utiliza Azul Zulu (el ID de -zulu arriba) o Amazon Corretto ( sdk install java 8.0.472-amzn ); ambos tienen compilaciones nativas de arm64. Para ver todas las compilaciones de Java 8 disponibles para tu máquina: sdk list java .

En Intel Macs / x64 Linux , Temurin 8 también funciona. ¿Prefieres un instalador GUI? Descarga Zulu 8 para tu arquitectura, o en Ubuntu/Debian sudo apt install openjdk-8-jdk .

Elija 3.29.2-GA . Es la versión con la que se construyó y probó este taller, y la que snapB / snapC ya está fijada. Ambas versiones son compatibles con Java 8, por lo que una más nueva no interrumpirá tu compilación actual, pero mantendrá a todo el grupo en una versión.

Hagas lo que hagas, no te saltes el cambio por completo , eso deja el hallazgo sin resolver.

Por qué el hallazgo de OGNL es un falso positivo: vale dos minutos

pom.xml de snapA ya fija ognl a 3.1.26 para compatibilidad con Struts 2.5.30, y lo dice en un comentario justo encima de la dependencia. La clase OgnlSecurityManager marcada existe en todas las versiones OGNL disponibles (3.1.26–3.4.11), por lo que la actualización no la eliminará. La llamada solo se produce en tiempo de ejecución en Java 18+ cuando en realidad está instalado un SecurityManager no nulo, lo cual Liberty nunca ocurre.

Entonces, el escáner tiene razón en cuanto a que el código existe, y está completamente equivocado en que importa aquí. Rechazar es la respuesta correcta , y es el momento más transferible en esta práctica de laboratorio: un hallazgo que es real y que es relevante para su tiempo de ejecución son dos preguntas diferentes, y solo tú puedes responder la segunda.

El hallazgo de javassist también es menos urgente de lo que parece.

Bob probablemente citará JEP 400 y "Java 17+" como motivo. Ten en cuenta que el Laboratorio 1 permanece en Java 8 : el juego de caracteres predeterminado no cambió a UTF-8 hasta Java 18, por lo que el error que describe no puede afectarlo en este laboratorio. AMA lo marca porque está planeando un objetivo Liberty que podría ejecutar una JVM más nueva.

Aprobar sigue siendo correcto (es inofensivo y es real), pero no permita que el encuadre de "desajustes silenciosos en el conjunto de caracteres" convenza a la sala de que evitaron un error real.

Punto de control: cómo se ve una nueva plataforma terminada

  • pom.xml tiene el io.openliberty.tools:liberty-maven-plugin .
  • src/main/liberty/config/server.xml existe, con la aplicación simple-pharmacy.war y las funciones Liberty.
  • maven.compiler.source / target son todavía 1.8 , y el código aún importa javax.servlet.* : el Laboratorio 1 no cambia ni la versión de Java ni el espacio de nombres.
  • El panel carga y enumera datos.

Detén el servidor antes de continuar

Libera el puerto para que el siguiente laboratorio no esté bloqueado.

  • macOS, Linux o WSL: presiona Ctrl + C en el terminal en ejecución Liberty. Si el puerto permanece retenido: lsof -ti:9080 | xargs kill -9 .
  • Windows (PowerShell): presiona Ctrl + C ; si el puerto permanece ocupado, ejecuta mvn liberty:stop o netstat -ano | findstr :9080 y luego taskkill /PID <pid> /F .

Solución de problemas

  1. Confirma que Maven esté instalado: mvn --version . En macOS/Linux (SDKMAN!) verifica sdk version y reinstala con sdk install maven ; en Windows reinstala con winget install Apache.Maven .
  2. Reinicia tu IDE/Bob completamente y abre una nueva terminal para que se recoja el PATH actualizado.
  3. Verifica nuevamente: mvn --version .
La terminal de Bob usa la versión de Java incorrecta

sdk use java <id> solo se aplica al shell en el que se ejecutó: la terminal de Bob es un shell separado. Ejecútalo en la terminal de Bob específicamente: 

          sdk use java 8.0.504+1-zulu

O establece el valor predeterminado global para que cada nuevo shell lo recoja:

          sdk default java 8.0.504+1-zulu
Bob no puede leer archivos de proyecto ( I cannot access that file / File not found )
  1. Verifica que el campo Project path del workflow apunta a snapA-java-liberty-replatforming (no a la carpeta general del workshop ni a lab1-* ).
  2. Verifica los permisos del archivo: ls -la .
  3. Asegúrate de que Bob tenga acceso de lectura al espacio de trabajo.
  4. Intente hacer referencia a archivos con la sintaxis @filename .
Unable to access jarfile al proporcionar la ruta ZIP AMA

SRVE0321E: The [struts2] filter did not load during start up

Es seguro ignorarlo. La aplicación migrada funciona correctamente; esto refleja un efecto secundario de la carga de clases que no afecta el comportamiento en tiempo de ejecución.

CWWKS9660E: The orb element with the defaultOrb id attribute requires a user registry

Es seguro ignorarlo, siempre que la aplicación no utilice componentes EJB basados en ORB, y éste no lo hace.

La compilación falla con invalid target release: 21 / Bob dice \"Java 21 no está disponible\"

El recipeConfig/rewrite.yml del plan de migración enumera las recetas OpenRewrite Java upgrade ( Java8toJava11 , UpgradeToJava17 , UpgradeToJava21 ). Estos pertenecen a Lab 2 : el Laboratorio 1 permanece en Java 8 con el espacio de nombres javax.* . Si se aplican, pom.xml cambia a Java 21 y el compilador de Java 8 no puede apuntar a una versión más reciente.

Esta es deriva de la receta , no un JDK faltante : no instales ni cambies a Java 21 aquí. Revierte el pom a Java 8:

  • Configura maven.compiler.source / target y el complemento del compilador maven <source> / <target> todos de nuevo en 1.8 .
  • Mantén el espacio de nombres javax.* .

mantenga el espacio de nombres javax.* y elimine cualquier mejora javassist/asm más allá de la solución aprobada

Luego reconstruye con mvn clean package .

La compilación falla con Unsupported class file major version

Maven se ejecuta en un JDK posterior a 8. Lab 1 permanece en Java 8 ; apunta Maven hacia él.

  • macOS / Linux (SDKMAN!): sdk use java 8.0.504+1-zulu
  • Windows: configura JAVA_HOME en tu carpeta Temurin 8 y vuelve a abrir la terminal, o ejecuta sdk use java 8.0.504+1-zulu si instalaste a través de SDKMAN! en Git Bash/WSL.

Luego reconstruir:

          mvn clean package

Confirma con mvn --version (imprime la versión de Java que está usando Maven, que puede diferir de la java -version de tu shell).

El flujo de trabajo propone un cambio y no estás seguro

Siempre que Bob ofrezca "muéstrame las ediciones exactas antes de aplicarlas" , tómalo: Bob presenta la diferencia completa para revisarla antes de tocar cualquier archivo. También puedes simplemente hacerle una pregunta de seguimiento en el chat; el flujo de trabajo espera.

Address already in use / el puerto no se liberará después de Ctrl+C

Una ejecución Liberty anterior todavía lo mantiene.

  • macOS, Linux o WSL: lsof -ti:9080,9443 | xargs kill -9 .
  • Windows (PowerShell): mvn liberty:stop . Si el puerto permanece ocupado: netstat -ano | findstr :9080 , entonces taskkill /PID <pid> /F .

No ignores este: hace que cualquier solución posterior parezca fallida

Si se toma el puerto, tu nuevo servidor nunca lo vincula y el antiguo sigue respondiendo. Editarás archivos, reconstruirás, reiniciarás y no verás ningún cambio, porque todavía estás hablando con el servidor obsoleto. Cada vez que una solución "no hace nada", verifica si hay un Liberty primero .
