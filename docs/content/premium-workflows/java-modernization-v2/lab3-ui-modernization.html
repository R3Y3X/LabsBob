Caso de uso: migrar Struts a React

La aplicación utiliza actualmente:

  • Interfaz : Struts / Representación del lado del servidor JSP

Lo migrarás a:

  • Interfaz : React SPA con Material UI
  • Backend : servicios REST estilo Jakarta EE (JAX-RS), reemplazando la capa de acción Struts como fuente de datos de la interfaz de usuario

Por qué esto importa

  • Struts es un marco MVC renderizado por servidor cuyo impulso empresarial se detuvo hace años. La presentación y la lógica empresarial están entrelazadas en acciones y JSP.
  • A React SPA en un backend REST separa los dos claramente: la capa Java se convierte en una API y la interfaz de usuario se convierte en una interfaz implementable de forma independiente. Esa división es lo que hace posible el resto de la modernización (contenedores, escalamiento independiente, un sistema de diseño).

404 en /api/… ? Es la raíz del contexto, no una API rota

Los pines server.xml enviados context-root="/simple-pharmacy" , por lo que la URL anterior es correcta. Pero si Bob reescribió server.xml y dejó la aplicación implementada como simple-pharmacy.war , Liberty la sirve en una raíz diferente ; siempre tome la raíz real del registro de inicio: 

          grep CWWKT0016I target/liberty/wlp/usr/servers/defaultServer/logs/messages.log

Si esa línea dice .../simple-pharmacy.war/ , use http://localhost:9081/simple-pharmacy.war/api/dashboard o agregue context-root="/simple-pharmacy" al elemento <application> en src/main/liberty/config/server.xml y reinicie.

Bonificación: la interfaz de usuario de Swagger en /openapi/ui/ : útil, pero es no la URL de backend

Si Bob habilitó la función mpOpenAPI (normalmente lo hace), Liberty ofrece una Swagger UI interactiva en la raíz del servidor . Nota: no hay ruta de contexto de la aplicación: 

          http://localhost:9081/openapi/ui/

Es fantástico para explorar y probar todos los puntos finales. Pero es la API documentación , no el punto final de datos que consume su aplicación React; eso es /simple-pharmacy/api/… . Y debido a que Liberty lo sirve (no su aplicación), devuelve 200 incluso cuando la API en sí es 404ing , así que no lo use como verificación de estado. Confirme el backend con el JSON /api/dashboard anterior.

Solución de problemas

CWWKS9660E: The orb element ... requires a user registry al iniciar el backend

Bob configuró el servidor con la plataforma completa jakartaee-10.0 , que incorpora el Pila ORB/EJB. El ORB espera 10 segundos por un registro de usuarios, no encuentra ninguno y registra "no se iniciará ninguna aplicación". Esta aplicación es REST + JSP solamente ; nunca usa EJB ni ORB - Entonces, el conjunto de funciones correcto es Web Profile . En src/main/liberty/config/server.xml , reemplace la función de la plataforma con el perfil web: 

          <feature>webProfile-10.0</feature>

Mantenga todas las funciones mpOpenAPI-* / mpMetrics-* : las funciones MicroProfile funcionan junto con ellas. Reiniciar Liberty; el error desapareció y el inicio es más rápido. La instantánea enviada ya utiliza webProfile-10.0 ; esto solo reaparece si Bob lo cambió por jakartaee-10.0 .

La solicitud de API falló: el chat muestra {\"apiProtocol\":\"openai\"}

Haga clic en Reintentar en la ventana de chat de Bob.

Cada llamada /api devuelve 404

Dos causas diferentes producen esto: verifique primero la raíz del contexto, es la más rápida:

1. Raíz de contexto incorrecta (más común una vez que Struts desaparece). Si Bob implementó la aplicación como simple-pharmacy.war , la base real es /simple-pharmacy.war/api/… , no /simple-pharmacy/api/… ; la línea de inicio CWWKT0016I le indica cuál. La multa por carga de la página Swagger /openapi/ui/ es no tranquilizadora aquí: Liberty la sirve en la raíz del servidor, por lo que funciona incluso cuando cada /api enruta 404. Solucione fijando context-root="/simple-pharmacy" en el elemento <application> en src/main/liberty/config/server.xml (la instantánea enviada ya hace esto).

2. Struts está tragando /api (solo si Struts todavía está en web.xml ). El filtro Struts asignado a /* intercepta las solicitudes REST antes de que JAX-RS las vea. Pregúntale a Bob: 

          Struts está interceptando /api antes de que JAX-RS lo vea. Agrega el struts.action.excludePattern
constante para /api y confirme que existe la clase activadora @ApplicationPath("/api").

Struts 7 coincide con excludePattern con el URI de solicitud completo (incluida la ruta de contexto), por lo que el patrón necesita un .* — .*/api/.* inicial, un /api/.* simple no.

El frontend no puede comunicarse con el backend: conexión rechazada/error CORS
  1. Confirme que el backend esté realmente activo: abra http://localhost:9081/simple-pharmacy/api/dashboard en un navegador y verifique que obtenga JSON.
  2. Confirme que ambos servidores se estén ejecutando a la vez: Liberty en 9081 y Vite en 3000.
  3. Si el navegador informa una falla de CORS, péguelo en Bob; el CorsFilter generado es el responsable y Bob lo conciliará.
npm run dev falla o la página está en blanco
  1. Confirma que estás en el Nodo 20 o 22 LTS: node --version .
  2. Asegúrese de que las dependencias estén instaladas limpiamente, desde la carpeta frontend, npm install .
  3. Pegue la salida de la consola (navegador y terminal ) en Bob.
Después del Paso 5, las páginas se crean pero no muestran datos (tablas/tarjetas vacías)

Primero, verifique en qué paso se encuentra : en el paso 4 aparece una página genérica vacía. esperado: las páginas de datos no existen hasta el Paso 5, por lo que no hay nada que depurar allí. esto la entrada es para cuando Bob haya terminado de construir las páginas (Paso 5) y estén todavía vacías.

En ese momento, el shell React se procesa pero las llamadas a /api fallan silenciosamente. Abre tu DevTools → pestaña Red del navegador y vuelva a cargar; si las solicitudes /api/... son 404 , es casi siempre es una falta de coincidencia de ruta, no un error de código. Un curl a través del servidor de desarrollo le dice cuál: 

          curl http://localhost:3000/api/dashboard

JSON atrás → el proxy y el backend están de acuerdo; el problema es la deriva del nombre del campo (ver más abajo). 404 → el proxy Vite y la raíz del contexto del backend no están de acuerdo. vite.config.ts reescribe /api/* → /simple-pharmacy/api/* , por lo que la aplicación solo funciona cuando Liberty implementó WAR en raíz de contexto /simple-pharmacy . Si Bob lo dejó como simple-pharmacy.war (verifique el CWWKT0016I línea de inicio), cada llamada al 404 y las páginas permanecen en blanco. Arreglar fijando context-root="/simple-pharmacy" en el elemento <application> en server.xml - el La instantánea enviada ya hace esto, por lo que coincide con el proxy, luego reinicia Liberty .

Una página /openapi/ui/ que funcione no es prueba de que la API funcione

Liberty sirve la interfaz de usuario de Swagger en la raíz del servidor, por lo que se carga incluso en cada ruta /api 404. Confirme siempre con el curl de arriba, no con la página Swagger.

contra lo que esperan los componentes React y conciliarlos.

Conclusiones clave

  1. El flujo de trabajo realiza la planificación, no solo la escritura : analiza la aplicación Struts, documenta la arquitectura y propone estados objetivo antes de escribir una línea de código.

  3. Primero el backend, luego el frontend : el flujo de trabajo descompone el monolito Struts en servicios REST y los vuelve verdes antes de construir la interfaz de usuario, por lo que el frontend tiene un contrato real sobre el cual construir.
  4. Por fases y revisable — Análisis → Planificación → Generación → Validación, con una lista de tareas pendientes que puede expandir en cualquier punto para ver exactamente dónde está Bob.
  5. Guía iterativa : pegar errores nuevamente en el chat es el flujo de trabajo previsto, no un modo de falla.
