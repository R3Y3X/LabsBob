Objetivos de aprendizaje

Escenario

Galaxium Travels es una aplicación que creció durante varios años en un codebase complejo. Una revisión manual de seguridad consume tiempo y produce resultados inconsistentes entre miembros del equipo. Necesitas un proceso repetible que genere salida estructurada que los desarrolladores puedan actuar de inmediato y que alimente un pipeline de remediación automatizado.

En este lab usarás IBM Bob para crear un skill de auditoría basado en OWASP ASVS, ejecutarlo contra Galaxium Travels, generar un reporte SARIF y producir un OSCAL Plan of Action and Milestones (POA&M) que Bob puede usar para guiar la remediación.

Alcance de la auditoría

Este lab audita contra ASVS Level 1 en control de acceso (V4), validación de inputs (V5), seguridad de API (V13) y configuración (V14). El mismo patrón de skill funciona con cualquier estándar: reemplaza los controles ASVS por CWE Top 25, un checklist interno u otro framework.

Ejercicio: Auditoría ASVS con skills y reportes estructurados

Paso 1 — Crear el skill de auditoría

Un skill es un conjunto de instrucciones reutilizable que Bob sigue para una tarea específica. Vas a crear asvs-audit para auditar Galaxium Travels contra OWASP ASVS Level 1.

  1. Bajo el chat, haz clic en Bob - Settings → Bob Settings.
  2. Haz clic en Skills en la barra lateral.
  3. Haz clic en + para crear un skill nuevo.
  4. Skill Name: asvs-audit (se invoca con /asvs-audit en el chat).
  5. Description:
Audita un codebase contra OWASP ASVS Level 1 en control de acceso, validación de inputs, seguridad de API y configuración.
  1. Activa Allow Bob to use this skill (permitir que Bob use este skill) para que pueda invocarlo cuando un plan o prompt lo requiera.
  2. Scope & Location: selecciona el proyecto galaxium-travels para guardar el skill en .bob/skills/ y versionarlo con el codebase.
  3. Pega las instrucciones completas del skill en Skill Instructions:
---
name: asvs-audit
description: Audita un codebase contra OWASP ASVS Level 1 en control de acceso, validación de inputs, seguridad de API y configuración, y produce hallazgos estructurados listos para exportar a SARIF y OSCAL.
user-invocable: true
---

Realiza una auditoría de seguridad estructurada de este codebase. Recorre las fases siguientes en orden. No las saltes ni las combines.

## Fase 1: Descubrir
Lee y entiende la aplicación antes de auditar. Concéntrate en:
- Puntos de entrada: archivos principales, definición de rutas, controladores
- Código de autenticación y manejo de sesión
- Código de validación y sanitización de inputs
- Código de consultas a base de datos
- Cualquier archivo marcado como de alto riesgo en un análisis previo

Resume lo que encuentres antes de pasar a la Fase 2.

## Fase 2: Auditar
Revisa cada control de abajo. Para cada uno registra: PASS, FAIL o N/A.
En cada FAIL, registra la ruta del archivo y el número de línea.

### V4.1 General Access Control
- V4.1.3 — Las personas usuarias solo acceden a sus propios recursos; los datos de otras no son accesibles
- V4.1.5 — El control de acceso deniega por defecto: las peticiones no autenticadas se rechazan

### V4.2 Operation Level Access Control
- V4.2.1 — Los recursos sensibles no se pueden acceder manipulando un ID de objeto predecible (protección IDOR)

### V5.1 Input Validation
- V5.1.1 — Todos los inputs de texto tienen una longitud máxima definida

### V13.1 Generic Web Service Security
- V13.1.3 — Los endpoints de API no aceptan credenciales ni PII en query params de URL

### V14.4 HTTP Security Headers
- V14.4.1 — Las respuestas HTTP incluyen headers de seguridad apropiados, como Content-Security-Policy, X-Frame-Options y X-Content-Type-Options

### V14.5 HTTP Request Header Validation
- V14.5.3 — El origen CORS se valida contra una allowlist explícita: no se permiten wildcards

## Fase 3: Generar hallazgos
Por cada FAIL, produce un hallazgo en este formato:

**Hallazgo [N]:**
- Regla: ASVS [número de control]
- Severidad: Critical / High / Medium / Low
- Archivo: [ruta]
- Línea: [número o rango, si se identifica]
- Problema: [una frase describiendo lo encontrado]
- Corrección: [una frase describiendo el cambio recomendado]

## Fase 4: Resumen
Produce un resumen corto:
- Total de controles revisados
- Conteos Pass / Fail / N/A
- Evaluación de la postura de seguridad en dos frases

Guarda los hallazgos en la ubicación que indique el plan o el prompt que invocó este skill. No generes SARIF, OSCAL ni otros reportes: la generación de reportes es una tarea aparte. Informa que la auditoría está completa y espera la siguiente instrucción.

Haz clic en Create.

Paso 2 — Identificar áreas de alto riesgo (Ask Mode)

Para ahorrar tokens, pide a Bob que identifique los archivos y carpetas más relevantes para seguridad antes de ejecutar el skill de auditoría.

  1. Abre el chat de Bob si no está visible.
  2. Selecciona Ask en el selector de modos.
  3. Envía este prompt:
Explora este codebase como Senior Security Analyst. Dame un resumen corto que cubra:
1. El stack y el framework principales
2. Los archivos y carpetas más relevantes para seguridad

Revisa también:
1. Cómo se manejan la autenticación y las sesiones
2. Cómo se aceptan y validan los inputs de usuario
3. Dónde se hacen las consultas a la base de datos
4. Cualquier endpoint de API que acepte input externo

Quiero entender las áreas de mayor riesgo de seguridad antes de ejecutar una auditoría.

Salida esperada

Bob lee los archivos y responde con un resumen de la estructura de la aplicación y las áreas de mayor riesgo.

Crea un plan para auditar las áreas de alto riesgo identificadas

Al auditar, usa el skill asvs-audit para guiar el proceso.

Cuando se ejecute el plan, crea el directorio security/ si no existe

Guarda el plan en plan/audit-plan.md

Paso 4 — Ejecutar la auditoría (Agent Mode)

  1. Haz clic en + para iniciar una tarea nueva.
  2. Selecciona Agent Mode.
  3. En Permissions, activa Read, Edit, Execute y Skill. Deja el resto desactivado.
PermisoEstadoPor qué
Read✅ OnBob lee el codebase, el plan y el skill
Edit✅ OnBob escribe los hallazgos en security/audit-findings.md
Execute✅ OnBob puede ejecutar comandos para confirmar estructura de archivos
Skill✅ OnEl plan invoca el skill asvs-audit
MCP❌ OffNo necesario para análisis local de código

Pide a Bob que implemente el plan:

Implementa el @plan/audit-plan.md

Revisa los hallazgos en security/audit-findings.md.

Ventana de contexto

Guardar los hallazgos en un archivo te permite iniciar un chat nuevo y generar reportes sin releer todo el codebase. En codebases grandes, audita una categoría ASVS a la vez (V4, luego V5, V13, V14) y pide a Bob que consolide al final.

Agent Mode requiere aprobación

Cada escritura de archivo mostrará un diff para que lo revises antes de confirmar.

Paso 5 — Generar reporte SARIF (Agent Mode)

SARIF es el formato estándar de intercambio para resultados de análisis estático. IDEs, GitHub Advanced Security y la mayoría de pipelines CI/CD lo consumen directamente.

  1. Inicia una tarea nueva con +.
  2. Usa Agent Mode.
  3. En Permissions, activa Read, Edit y Execute. Deja Skill y MCP desactivados.
@security/audit-findings.md

Genera un reporte SARIF 2.1.0 a partir de los hallazgos de la auditoría.
Guárdalo en `security/audit-results.sarif`.

Incluye:
- Nombre de la herramienta: "ASVS Security Audit"
- Una entrada de regla por cada control ASVS revisado, con el ID del control y su descripción
- Una entrada de resultado por cada hallazgo, con nivel de severidad, ruta de archivo, número de línea y la corrección recomendada en el campo message

Salida esperada

El archivo security/audit-results.sarif debe contener un array runs con entradas results, una por hallazgo. Bob suele mapear Critical/High → SARIF error y Medium/Low → SARIF warning.

Paso 6 — Generar plan de remediación OSCAL POA&M (Agent Mode)

El POA&M OSCAL es un documento JSON legible por máquinas que mapea cada hallazgo a una tarea de remediación estructurada. Bob puede leerlo como cola de trabajo y aplicar correcciones sistemáticamente.

  1. Inicia una tarea nueva con +.
  2. Usa Agent Mode.
  3. En Permissions, activa Read, Edit y Execute.
@security/audit-findings.md

Genera un Plan of Action and Milestones (POA&M) OSCAL a partir de los hallazgos de la auditoría.
Guárdalo en `security/poam.json`.

Para cada hallazgo incluye:
- Un UUID único
- El ID del control ASVS como referencia del hallazgo
- Severidad y una descripción del riesgo en una frase
- Una tarea de remediación concreta, con detalle suficiente para que un agente de IA la implemente sin contexto extra: incluye ruta de archivo, referencia de línea y el cambio específico requerido
- Una etiqueta de hito según severidad: Critical y High reciben "sprint-1"; Medium y Low reciben "sprint-2"

Usa la estructura de OSCAL versión 1.1.2.

Al terminar tendrás dos artefactos en security/:

  • audit-results.sarif — hallazgos estructurados para tooling y CI/CD
  • poam.json — cola de remediación para asistencia humana o por IA

Paso 7 — Revisar y priorizar hallazgos (Ask Mode)

  1. Inicia una tarea nueva con +.
  2. Selecciona Ask Mode.
  3. Envía este prompt:
@security/poam.json

Revisa este plan de remediación e identifica los 3 ítems más críticos para corregir primero.

Para cada uno incluye:
- Qué vulnerabilidad es y por qué es la de mayor prioridad
- Qué archivo y línea hay que mirar
- En qué consiste la corrección y cuánto tardaría aproximadamente una persona desarrolladora en implementarla

Siguiente paso opcional

También puedes integrar un servidor MCP y pedir a Bob que cree tickets por hallazgo, enlazando el código relevante y la guía de remediación del POA&M.
