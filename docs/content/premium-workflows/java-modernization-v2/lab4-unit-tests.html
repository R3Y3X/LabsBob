Laboratorio 4 — Generación de pruebas unitarias

Genera una suite completa de tests JUnit 5 / Mockito / AssertJ para la aplicación de farmacia modernizada con el workflow Java Unit Testing, y analiza la cobertura con JaCoCo.

Objetivo JUnit 5
~20 minutos
10–12 BobCoins estimados
Premium acceso requerido

Introducción

Genere un conjunto de pruebas completo JUnit 5 / Mockito / AssertJ para la aplicación de farmacia modernizada utilizando el flujo de trabajo independiente Java Unit Testing de Bob, luego analice la cobertura con JaCoCo.

Lo que lograrás

Ejecute el flujo de trabajo Java Unit Testing de un extremo a otro: Bob instala JaCoCo, redacta una estrategia de prueba UNITTEST.md , genera pruebas en lotes paralelos, corrige sus propias fallas de compilación, ejecuta la suite e informa la cobertura por clase.

Este es un flujo de trabajo de nivel superior, no un subtipo.

Java Unit Testing se encuentra junto a Java Modernization en la lista de flujo de trabajo; no está anidado dentro de él. (También aparece como un subtipo dentro de Java Modernization; cualquiera de los puntos de entrada funciona, pero esta práctica de laboratorio utiliza el de nivel superior).

Cómo funciona el flujo de trabajo

Vale la pena entenderlo antes de ejecutarlo: el flujo de trabajo Java Unit Testing se desarrolla en nueve fases:

  1. Análisis de proyecto : analiza la estructura, la herramienta de construcción y la infraestructura de prueba existente (versión JUnit, JaCoCo, Surefire).
  2. Generación de estrategia de prueba : produce UNITTEST.md que define patrones de nomenclatura, enfoque burlón, reglas de aislamiento y alcance.
  3. Pantalla de selección de tareas : usted elige qué ejecutar (generar estrategia, generar pruebas, ejecutar cobertura, Git Flow) y una Estrategia de selección de candidatos .
  4. Vista previa de costo/tiempo : duración esperada y costo de Bob-coin con un intervalo de confianza del 80% .
  5. Generación de prueba (subagentes por lotes) : subagentes paralelos por paquete, cada uno de los cuales lee la clase de producción y UNITTEST.md .
  6. Actualizaciones de compilación y dependencia : agrega las dependencias de prueba que faltan a pom.xml según sea necesario.
  7. Tareas de recuperación autocorregibles : si encuentra archivos de clase obsoletos o compila carreras a mitad de ejecución, agrega subtareas de recuperación y las corrige sin que se le solicite.
  8. Ejecución y validación de pruebas : ejecuta mvn test y corrige fallas antes de continuar.
  9. Informe de cobertura : ejecuta la suite con JaCoCo y muestra la cobertura de instrucción por clase.

2.4 Vista previa de costo/tiempo

Bob muestra una estimación del siguiente tenor:

"Generaré pruebas unitarias para 12 clases en 4 lotes. Para cada lote, espero una duración de 3 minutos y un costo de 2,8 monedas de Bob (el 80% de los lotes terminan dentro de estos límites)".

Haga clic en Continuar con la generación de prueba .

Tenga en cuenta el intervalo de confianza del 80 %: está funcionando de verdad

Bob está diciendo explícitamente que un lote de cada cinco puede durar más o costar más. Es una estimación, no una garantía y, en la práctica, el costo real generalmente cae muy por debajo de la vista previa (por ejemplo, ~4,5 monedas frente a una estimación de ~11 monedas).

Vale la pena señalarlo en una sala: los informes de variación honestos son poco comunes en las herramientas de inteligencia artificial, y existen para que pueda realizar una llamada de ir/no ir antes , una operación costosa en lugar de descubrir la factura después.

Paso 3: revisar la estrategia y los resultados

3.1 Leer UNITTEST.md

Abra UNITTEST.md en la raíz del proyecto. El documento de estrategia de Bob cubre:

  • Resumen de la arquitectura de la aplicación
  • Clases comprobables y sus responsabilidades.
  • Convenciones de nomenclatura y rutas de archivos de prueba
  • Umbrales de cobertura (metas, no garantías)
  • Brechas identificadas priorizadas como P1/P2/P3
Este archivo es el verdadero artefacto.

Las pruebas son el resultado, pero UNITTEST.md es el razonamiento . Es lo que hace que un ser humano pueda revisar y ampliar la suite más adelante, y es lo que lee cada subagente de generación para mantenerse coherente con los demás. Sin él, los agentes paralelos inventarían cada uno sus propias convenciones.

3.4 Explorar un archivo de prueba generado

Abra algunas pruebas generadas (por ejemplo, src/test/java/com/pharmacy/repository/PrescriptionRepositoryTest.java ) y tenga en cuenta:

  • @ExtendWith(MockitoExtension.class) en la clase de prueba

Mira cómo Bob se burló de los solteros.

Los repositorios utilizan el patrón singleton, que es realmente complicado de probar. Una técnica común es MockedStatic combinada con reflexión para sobrescribir el campo singleton privado. Vale la pena leerlo atentamente: es la parte de la suite generada con mayor probabilidad de enseñarle a un desarrollador Java experimentado algo que aún no sabía.

Verifique algunas pruebas para confirmar que siguen convenciones sólidas: nombres claros, casos aislados, afirmaciones significativas.

Solución de problemas

La solicitud de API falló: el chat muestra {\"apiProtocol\":\"openai\"}

Haga clic en Reintentar en la ventana de chat de Bob.

mvn test informa \"no se puede encontrar el símbolo\" o faltan clases

Archivos .class obsoletos de una ejecución anterior. Forzar una recompilación completa: 

          mvn clean test
Fallos de inyección simulada: NullPointerException al acceder a objetos simulados
  1. Asegúrese de que @ExtendWith(MockitoExtension.class) esté presente en la clase de prueba.
  2. Verifique que las anotaciones @Mock y @InjectMocks sean correctas.
  3. Verifique que los simulacros estén inicializados en @BeforeEach si no usa la extensión.
  4. Pídale a Bob que revise la configuración simulada.
Las pruebas pasan individualmente pero fallan cuando se ejecutan juntas

Los singleton del repositorio mantienen el estado entre pruebas. Opciones:

  1. Agregue métodos de reinicio a los repositorios o use la reflexión para restablecer instancias.
  2. Pídale a Bob que implemente un aislamiento de prueba adecuado.
  3. Considere @TestInstance(Lifecycle.PER_CLASS) con una limpieza adecuada.
Informe de cobertura de JaCoCo no generado: no hay directorio target/site/jacoco/

El informe necesita explícitamente el objetivo jacoco:report ; mvn test por sí solo no lo producirá. 

          mvn clean test jacoco:report
La terminal de Bob muestra la versión de Java incorrecta

sdk use tiene un alcance de shell: no se aplica a las pestañas del terminal ni al terminal que Bob abre por sí solo. Ejecútelo en la terminal de Bob específicamente: 

          sdk use java 21.0.11-zulu

  • mvn clean test pasa con 0 fallas, 0 errores .

Conclusiones clave

  1. Estrategia antes de las pruebas - UNITTEST.md es lo que mantiene a los subagentes paralelos consistentes entre sí. El documento es tan entregable como lo son las pruebas.
  2. Subagentes por lotes : contextos aislados por paquete significan que Bob puede generar un conjunto completo sin que una ventana de contexto gigante pierda la trama.
  3. Estimaciones de costos honestas : el intervalo de confianza del 80 % le permite decidir antes de gastar. El costo real generalmente se ubica muy por debajo de la vista previa.
  4. Autocorrección : el flujo de trabajo agrega subtareas de recuperación no planificadas cuando la compilación se interrumpe a mitad de ejecución, en lugar de entregarle un árbol roto.
  5. La cobertura es un punto de partida, no un trofeo : el 80 % con afirmaciones significativas supera el 95 % de las pruebas de obtención. Lea lo que se generó.
